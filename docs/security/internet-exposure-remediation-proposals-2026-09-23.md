# Internet-exposure remediation proposals

Prepared 2026-09-23 for findings F1–F7 in the [source review](internet-exposure-review-2026-09-23.md). The sections below are **reference proposals, not a description of current controls**. The selected F1/F2/F4/F5/F7 changes and their limits are tracked in the [2026-09-24 implementation status](internet-exposure-hardening-status-2026-09-24.md). The objective is to make remote desktop viewing and input defensible, whether the host is directly Internet-reachable or uses a relay. A TLS padlock alone is not a release criterion: signaling, account admission, host control, diagnostics, and WebRTC media cross different trust boundaries.

The owner selected an [interim hardening design for F1, F2, F4, F5, and F7](../superpowers/specs/2026-09-23-selected-internet-exposure-hardening-design.md) and an [F2/F4/F5 follow-up](../superpowers/specs/2026-09-24-revocation-and-diagnostics-isolation-design.md); see the [current implementation status](internet-exposure-hardening-status-2026-09-24.md). Eight-character codes remain host-issued on demand, short-lived, single-use, and attempt-capped; the standing session password is local-only. The owner deliberately chose a copyable **browser/client secret additional to username and password**, with revocation and one-session limits. It is not intended as a device credential or device-binding proof. This does not select a remote deployment profile or supersede F3/F6. Stronger invitation/passkey/TURN language below remains a reference proposal, not the selected client identity model.

## Proposed security contract

Add a distinct, opt-in `remote.enabled` mode, default `false`, with an explicit deployment profile. Turning it on must run a profile-specific startup preflight and expose a host-visible status of either **remote-ready** or **remote-disabled with reasons**. A degraded state must never silently serve remote clients over HTTP or switch to direct public media as an undocumented fallback. The original F1–F7 proposals below describe a **direct-public HTTPS+TURN reference design**, not a selected implementation. The alternatives in the next section may replace its public hostname/certificate, owner-configured TURN, or per-device approved-client workflow, but not the underlying requirements for authenticated transport, strong admission, current control permission, revocation, and bounded work. Keep LAN operation independent so a remote configuration failure does not turn a LAN-only installation into an insecure public service.

The suggested configuration names below are illustrative; fit them to the existing settings model, migration path, and Windows host UI. Persist secrets with appropriate Windows protection and file ACLs; never put a TURN shared secret, enrollment secret, or private key in `/api/info`, status pages, logs, or a world-readable settings file. Configuration validation should fail closed, not silently substitute development defaults.

**SecRAC** means _Security-Related Application Conditions_: security conditions the application can guide, check, or help configure, but cannot fully establish on its own. They are explicitly secondary to the program-enforced changes. The host UI should show each unmet SecRAC as a warning or a remote-mode blocker where it can be verified.

| Finding | Program-enforced outcome                                              | Direct-public baseline gate                         |
| ------- | --------------------------------------------------------------------- | --------------------------------------------------- |
| F1      | No unmetered key oracle or short-key remote login                     | Required                                            |
| F2      | Current permission immediately governs every control lease            | Required, including LAN                             |
| F3      | HTTPS-only public admission; trust enrollment stays local             | Required                                            |
| F4      | Public path cannot reach host diagnostics                             | Required                                            |
| F5      | Remote identity cannot be treated as merely a copyable browser record | Required for the proposed approved-device guarantee |
| F6      | WebRTC transport uses an authenticated relay-only policy              | Required for remote media                           |
| F7      | Bounded, expiring work and public-edge budgets                        | Required                                            |

## Deployment profiles and alternatives

The hostname/certificate, TURN, and approved-client enrollment called out in the direct-public reference design are **not a universal three-part prerequisite**. The software may provide equivalent controls through another architecture. **No remote deployment profile has been selected or implemented.** The owner does not currently favor the VPN-only or product-operated outbound-relay options; both are retained for comparison, not treated as decisions. None of these profiles makes authentication optional.

### Product-operated outbound relay — retained option, not selected

The Windows host maintains an **outbound-only**, authenticated TLS connection to a product-operated rendezvous service. The viewer opens the service's ordinary HTTPS site; the service relays signaling and provides authenticated, short-lived TURN allocations for WebRTC media. Both browser and native worker use relay-only ICE. The host needs no public inbound VidVNC port, DNS name, public certificate, router rule, or operator-configured TURN server. The service operator—not the end user—must run and secure the public HTTPS, identity, rendezvous, and TURN infrastructure. The host's existing `0.0.0.0` HTTP listener must still be changed or firewalled so the relay profile does not leave a separate public route into the PC.

For a viewer that may connect **only while the owner is at the host**, replace persistent approved-client enrollment with a high-entropy, one-use invitation and local approval for each session. For **unattended** access, the host must pre-authorize a durable identity: for example, an owner account protected by a passkey and locally bound to that host, with explicit view/control policy, session visibility, and one-step revocation. This removes a _separate per-browser approved-client enrollment step_, not the need for any prior authorization. The host should enforce its own authorization decision rather than accepting a relay's claim as the sole grant of desktop control.

The relay sees connection metadata and traffic volume. WebRTC's DTLS/SRTP protects media from passive TURN inspection, but a signaling service can substitute peer fingerprints unless endpoints independently authenticate them; a service that delivers the browser JavaScript could also serve altered client code. Therefore **do not claim the hosted service is unable to view/control sessions** without an independently trusted viewer and verified endpoint-key binding. Treat service compromise, account takeover, outage, operating cost, abuse limits, and data-location policy as first-class SecRACs and threat-model items. [WebRTC security architecture](https://www.rfc-editor.org/rfc/rfc8827.html) identifies the signaling-server man-in-the-middle risk; [TURN](https://www.rfc-editor.org/rfc/rfc8656.html) specifies authenticated, finite allocations.

**Programmatic release tests:** no public inbound VidVNC socket or direct ICE packet on IPv4/IPv6; host reconnects outbound after relay interruption but never falls back to public HTTP/direct ICE; invitation replay and unknown account fail; owner revoke closes signaling, media, input, and relay credentials; compromised/invalid relay credentials cannot grant host control. A separate service-operator security review is required. This option reduces end-user network setup but requires a substantial new hosted subsystem and service trust; it is deferred, not a small setting change or an approved direction.

### VPN-only private remote — retained option, not selected

An authenticated VPN/mesh enrolls both devices; VidVNC binds only to its VPN interface and app/firewall policy denies non-VPN access. A locally trusted or out-of-band fingerprint-checked HTTPS certificate can replace a public CA certificate. Direct WebRTC over the private route may avoid a VidVNC TURN deployment, but must be validated across the supported VPNs and browsers; relay fallback in the VPN itself may still occur. VPN device identity plus app authentication or host approval can replace VidVNC's per-browser approved-client enrollment. F1, F2, F4, and F7 still need fixes. This profile avoids product-operated relay infrastructure but requires VPN installation/account administration on every viewer, which is a substantial usability cost. [Tailscale connection types](https://tailscale.com/docs/reference/connection-types) illustrate direct and encrypted relayed VPN paths. The owner must protect the VPN account/device list and prevent a separate non-VPN listener from remaining reachable.

### Direct public IP with automated certificate and direct ICE — lower infrastructure, lower reliability

For an owner who rejects both VPN and a hosted relay, a stable public IP can now obtain an automatically renewed, publicly trusted **IP-address certificate**; a DNS hostname is not mandatory. These certificates are valid for about six days, so renewal must be reliable and fail closed. Pairing can use a high-entropy invitation plus host approval, or a durable passkey-backed identity for unattended access. STUN/direct ICE with constrained public UDP may work without TURN, but NAT/firewall conditions can prevent connections, and it exposes the native ICE/DTLS/SRTP parser to public packets. The app would need port-range control, candidate/egress restrictions, dependency hardening, packet-capture tests, and explicit router/firewall setup. This is a possible advanced profile, **not** the recommended default or an equivalent reachability guarantee. [Let's Encrypt IP certificates](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability), [WebRTC peer connectivity](https://webrtc.org/getting-started/peer-connections).

## F1 — Eliminate the connection-key oracle and meter all admission attempts

**Code/configuration proposal.** In every remote profile, disallow the current short ordinary session and one-time keys as remote login methods. The direct-public baseline uses the approved-client flow; for initial enrollment, generate a CSPRNG invitation of at least 128 bits, single use and short lived, displayed by the host. A submitted invitation creates a pending request, not an approved account. The owner must still approve it locally. The outbound-relay profile may instead use per-session host consent or a pre-authorized strong owner identity as described above. Retain the short readable keys only for explicitly LAN-scoped workflows if needed.

Remove `/api/connection-key` from the public remote route set, or make it return a generic non-oracular response. Put a common admission limiter _before_ key parsing/inspection, password derivation, registration lookup, and other expensive work. Count malformed, unknown, expired, and valid-but-not-authorized attempts. Apply per-source, per-client/account, and instance-wide budgets with bounded storage, backoff/temporary suspension, and `429`/`Retry-After`; a distributed source rotation must still meet the instance-wide budget. Do not trust `X-Forwarded-For` unless the immediate peer is an explicitly configured trusted proxy. Responses should not reveal whether a key, account, or client ID exists.

**Where.** HTTP inspection and connect routes in [http-app.mjs](../../apps/server/src/http-app.mjs); key lifecycle in [connection-keys.mjs](../../apps/server/src/connection-keys.mjs); admission counters in [session-store.mjs](../../apps/server/src/session-store.mjs) and [approved-clients.mjs](../../apps/server/src/approved-clients.mjs).

**Acceptance tests.** Verify both inspection and connection endpoints exhaust the same intended budget for invalid and malformed guesses; parallel requests cannot exceed it; unknown identities are counted; changing source IP cannot bypass the global limit; valid attempts after throttling behave according to the documented lockout policy. Verify no remote request accepts a short session key.

**SecRAC.** An owner must convey enrollment invitations through an authenticated channel and reject unexpected approval requests. The host UI can make the invitation expire automatically, display its remaining lifetime, and require explicit approval with device/session details.

## F2 — Make view-only an immediate, enforced control boundary

**Code/configuration proposal.** Give each approved-client permission a monotonically increasing policy generation. A control grant must resolve the _current_ client, session, and generation immediately before `ControlLease.grant()`; it must not rely on the `automaticControl` value captured at admission. On a change to `view-only` or client removal, atomically prevent new grants, clear pending automatic eligibility, revoke every active lease and input channel for that identity, and require an acknowledgement from the native worker. If revocation cannot be confirmed promptly, terminate that peer/worker connection and mark the host action failed rather than displaying success. Lease renewal must re-evaluate effective permission and generation. Recheck after asynchronous operations to close grant/revoke races.

Give `approved-only` a separate **lock down now** operation that disconnects existing ordinary sessions and revokes their leases. Merely changing the future sign-in mode must not be presented as an emergency ejection. Expose the resulting live sessions and control owner in the host UI.

**Where.** [stream-runtime.mjs](../../apps/server/src/stream-runtime.mjs), [control-lease.mjs](../../apps/server/src/control-lease.mjs), permission/remove/mode commands and renewal in [main.mjs](../../apps/server/src/main.mjs), and the native input gate in [media-worker.cpp](../../native/media-worker/src/media-worker.cpp).

**Acceptance tests.** Downgrade before first stream selection, while a lease is active, and during an in-flight grant. In every case, subsequent input is rejected and no renewal re-enables control. Simulate a non-acknowledging worker; the connection must fail closed. Test client removal and the explicit lockdown path against multiple sessions.

**SecRAC.** The owner must use **revoke/disconnect** for an actively untrusted client, not assume that changing future sign-in mode evicts it. The UI should make this distinction and offer one-step emergency lockdown.

## F3 — Separate public HTTPS from local trust enrollment

**Code/configuration proposal.** The **direct-public** profile should start its public listener only after a configured public DNS name _or public IP certificate_, certificate chain, private key access, validity period, and HTTPS bind have passed preflight. Use the existing provided-certificate strategy or an automated public-CA integration; do not offer the local `mkcert` root or self-signed anchor as an Internet bootstrap method. If renewal, validation, or bind fails, disable remote admission and report the failure. Do not fall back to HTTP. If reverse proxy support is offered, define the trusted proxy addresses and exact public origin in configuration, and reject untrusted forwarding headers. The outbound-relay profile should instead authenticate its outbound service connection and never open a public host listener.

Disable trust-anchor enrollment by default in remote mode. If LAN clients still need it, allow the owner to enable `/trust`, `/api/trust/status`, and `/api/trust/anchor` on a **separate LAN enrollment listener** for a short enrollment window, protected by a one-time host-displayed enrollment code. Bind it to explicitly selected LAN interfaces and check the actual peer address against owner-configured CIDRs; do not rely on `Host`, `Origin`, or browser location to establish locality. The installer/host UI may offer a program-scoped Windows Firewall rule limited to Private profile and `LocalSubnet` or narrower CIDRs, with explicit administrator consent. The app-level address gate is still required because firewall rules can be altered or bypassed by proxying. A default-deny LAN listener is preferable to a listener on all interfaces with a warning. The code limits casual public proxying; it does **not** authenticate the downloaded anchor against an on-path attacker, so fingerprint comparison remains necessary.

On _every_ plaintext request, use the socket's security state to reject authentication, signaling, session, diagnostics, and media-related APIs before routing. Reject absolute-form targets on the plaintext listener—or normalize and apply the same deny policy—so `http://host/api/connect` cannot bypass the redirect. Treat redirects as convenience only. Keep trust-anchor bytes off the public listener entirely, including through a reverse proxy.

**Where.** Listener startup and fallback in [main.mjs](../../apps/server/src/main.mjs) and [TLS listener](../../apps/server/src/tls/listener.mjs); route and redirect logic in [http-app.mjs](../../apps/server/src/http-app.mjs); TLS settings in [tls-settings.mjs](../../apps/server/src/tls/tls-settings.mjs).

**Acceptance tests.** Simulate missing/expired certificate, failed renewal, HTTPS bind failure, and HTTP absolute-form request targets; no remote authentication request may succeed over HTTP. Test trust routes from allowed LAN, disallowed subnet, and a public request deliberately forwarded by a same-host proxy. The latter must not succeed without an active host-issued code, even if the proxy makes the socket look LAN-local. Confirm the host/firewall rule is narrower than `Any` where it is installed, and that failure to install it is surfaced rather than ignored. Test certificate rotation without exposing the private key or permitting downgrade.

**SecRAC.** For direct-public access, the owner must supply a DNS name or stable public IP and a valid publicly trusted certificate (or enable supported automated issuance), forward **only** the public HTTPS endpoint, and verify that the LAN enrollment listener is not Internet-routable, including through a local proxy. In the outbound-relay profile, the operator supplies public TLS and the owner must not expose an independent VidVNC listener. For LAN anchor installation, compare the fingerprint out of band on the host; do not treat the downloaded page as independent proof of itself. Programmatic preflight can test local binding and firewall configuration, but cannot prove every upstream router or cloud firewall rule.

## F4 — Remove diagnostics from the public request trust domain

**Code/configuration proposal.** In remote mode, do not mount `/diagnostics` or `/api/diagnostics` on the public listener. Move the data to local host UI/CLI or a separate management IPC channel. If a network diagnostics page is essential, require a dedicated owner authentication mechanism on an isolated management listener; loopback socket source and `Host: localhost` are not authentication. Make management routes unavailable through the normal reverse-proxy upstream even if the proxy rewrites `Host` and terminates on the same machine.

**Where.** Diagnostics guard and routing in [http-app.mjs](../../apps/server/src/http-app.mjs); host management channel in [main.mjs](../../apps/server/src/main.mjs).

**Acceptance tests.** A public request forwarded by a same-host proxy to `127.0.0.1` with `Host: localhost` must still receive no diagnostics data. Ordinary local owner access through the chosen management channel remains possible. No sensitive stream label, client address, or runtime diagnostic appears in unauthenticated public responses.

**SecRAC.** If the operator deploys a proxy, its route map must exclude the management surface. The app should expose a proxy configuration check and a test URL/status, but should not use that operator promise as its only guard.

## F5 — Give approved clients a meaningful possession factor and revocation model

**Code/configuration proposal.** Treat the current IndexedDB client secret as a copyable bearer credential, not a device identity. For a remote profile that retains approved clients, enroll a public-key credential and require a fresh challenge response at sign-in, bound to the configured public origin/RP ID and approved-client record. WebAuthn is a browser-native path; require user verification when supported and verify challenge, origin, RP ID, signature, and counter/backup metadata server-side. A passkey may be synced to another device, so do not claim strict physical-device binding from WebAuthn alone. If the product promises a particular machine, specify and test a non-exportable device-key policy and supported platform constraints; otherwise label it an approved _credential_. The outbound-relay profile may replace the approved-client list with host-local authorization of a strong owner account or per-session host consent, but must still bind each session to a revocable identity and current permission.

As an interim defense, enforce a configurable maximum of one active remote session per approved identity (with explicit takeover/revocation UX), show every live session to the owner, and revoke **all** sessions when an identity is removed or credential is rotated. Add a record generation checked before and after password derivation/session creation so concurrent removal cannot create a surviving session. Keep password verification and generic error responses during migration; do not equate the unverified `installationId` string with device binding.

**Where.** Registration/sign-in and credential records in [approved-clients.mjs](../../apps/server/src/approved-clients.mjs), session creation in [session-store.mjs](../../apps/server/src/session-store.mjs), browser enrollment/storage in [approved-client.js](../../apps/web-client/src/approved-client.js), and owner removal in [main.mjs](../../apps/server/src/main.mjs).

**Acceptance tests.** A copied IndexedDB record plus password alone cannot sign in to the remote profile after migration. Replayed, wrong-origin, wrong-RP-ID, and stale challenges fail. Concurrent sign-in and remove/rotate cannot leave a usable session. Owner revocation invalidates all live bearers and control leases; a second session follows the configured takeover policy. Explicitly test a synced passkey against the wording shown in the UI.

**SecRAC.** The owner must protect the approved authenticator and password and promptly revoke a lost credential. The host UI should report credential type and backup/sync status when available, so an owner can choose whether synced passkeys are acceptable.

## F6 — Make remote WebRTC relay-only and constrain native media exposure

**Code/configuration proposal.** The direct-public baseline requires an operator-configured TURN service; the outbound-relay profile supplies TURN as part of the product service, without end-user setup. Mint short-lived, per-session TURN credentials only after authenticated admission, scoped and expired with that session. Configure both browser peers with TURN and `iceTransportPolicy: "relay"`; configure GStreamer `webrtcbin` with its relay-only ICE transport policy and TURN server. Reject or fail a connection if relay-only behavior cannot be established—never fall back to direct host/srflx candidates in either relay profile. Keep DTLS/SRTP; TURN is a transport boundary, not a substitute for media encryption or authorization. Cap SDP size, parsing work, ICE negotiation count, data-channel rate, and peer lifetime. Test native GStreamer/libnice behavior rather than trusting browser policy alone. The VPN and direct-public-IP options replace this transport gate with their narrower network/candidate policies and the additional tests above; they are not implicit fallback modes.

Provide optional Windows Firewall/egress guidance or rule setup that limits the host's media traffic to the selected TURN endpoint and avoids arbitrary public UDP admission. Because firewall behavior depends on executable paths, profiles, IPv6, and administrator privileges, validate what the app can and report residual exposure. Keep native media libraries pinned and scanned separately from `npm audit`. For stronger host isolation, investigate running the SDP/ICE parser in a lower-privilege worker and issuing input through a narrowly scoped broker; only count that as a control if the OS process boundary genuinely limits `SendInput` and filesystem/network access.

**Where.** Browser peers in [stream-subscriptions.js](../../apps/web-client/src/stream-subscriptions.js), authenticated signaling in [http-app.mjs](../../apps/server/src/http-app.mjs), and native WebRTC setup/input in [media-worker.cpp](../../native/media-worker/src/media-worker.cpp).

**Acceptance tests.** For the direct-public HTTPS+TURN and outbound-relay profiles, packet captures on IPv4 and IPv6 show no direct browser-to-host media/ICE packets and no host ICE checks to client-supplied internal destinations. Missing TURN credentials or relay failure leaves the stream unavailable rather than switching to direct. Fuzz malformed SDP and ICE messages, and test unauthenticated packets against any listening media socket. Verify TURN credentials expire promptly; on session revocation, close the media peer immediately, stop issuing credentials, and revoke an existing TURN allocation where the chosen TURN service supports it. A TURN service that cannot revoke allocations leaves a bounded credential/allocation lifetime as residual risk. Apply the separately stated VPN/direct-ICE network tests to those profiles instead.

**SecRAC.** In the direct-public baseline, the owner needs a trustworthy TURN endpoint reachable by both sides and must not add broad public UDP forwarding to “make WebRTC work.” In the outbound-relay profile, the service operator owns TURN reliability and abuse controls; the owner still needs working outbound connectivity. The app can validate relay connectivity and show a precise error, but it cannot control every upstream network device.

## F7 — Bound public resource use and make admission state expire

**Code/configuration proposal.** Add a single public-request admission layer that caps requests, concurrent handshakes, body size, active scrypt jobs, pending registrations, concurrent SDP negotiations, streams, and total sessions before expensive work. Keep per-source/client counters bounded and expire them; reserve a global budget so filling the source map cannot indefinitely deny every new legitimate identity. Give pending, approved-but-unclaimed, and rejected registration claims explicit TTLs and periodic cleanup. Bound queued owner approvals and make duplicate registrations idempotent or reject them predictably. Preserve existing socket/header timeouts and per-listener connection caps, but add a deployment edge (or equivalent in-process protection) for volumetric connection/TLS-handshake abuse. Emit aggregate security metrics and safe audit events without credentials, SDP, passwords, or keys.

**Where.** Server limits in [server-limits.mjs](../../apps/server/src/server-limits.mjs), attempt maps in [session-store.mjs](../../apps/server/src/session-store.mjs) and [approved-clients.mjs](../../apps/server/src/approved-clients.mjs), and request admission in [http-app.mjs](../../apps/server/src/http-app.mjs).

**Acceptance tests.** Flood malformed requests, rotating source identities, pending registrations, slow bodies, and simultaneous scrypt/SDP work under configured limits. Memory and worker concurrency remain bounded; the server returns controlled `429`/`503` instead of exhausting the host; stale state ages out; a legitimate client can recover after the budget window. Test public edge and app limits together, including proxy-address handling.

**SecRAC.** A public deployment needs upstream DDoS capacity and monitoring that a desktop application cannot itself provide. The installer or host UI should give operator-facing guidance and warn when the public edge is absent, while the app still enforces its own finite work budgets.

## Delivery order and release decision

1. Fix F2's active-control revocation and F1's unmetered key admission first; they affect security even on a trusted LAN. Add an explicit emergency lockdown command.
2. Select and threat-model one deployment profile before implementing profile-specific F3/F5/F6 work. No profile is currently selected; in particular, neither VPN-only nor product-operated outbound relay is the chosen direction. Keep direct-public-IP as a separate advanced option. Once a profile is selected, build remote-mode preflight, listener separation, local-only enrollment, and diagnostics isolation (F3–F4). Remote mode remains disabled until these pass.
3. Add the selected profile's strong sign-in/consent and revocation (F5), media path and candidate policy (F6), and bounded admission/claim lifetimes (F7). Verify the entire signaling-to-input path under the profile's real network topology.
4. Perform a hardware/network exercise: TLS failure/renewal where applicable, Windows Firewall rules, IPv4/IPv6 packet capture, relay outage or direct-ICE failure, malformed signaling, account-removal races, and native dependency review. Publish remote mode only when all gates for its selected profile pass. An external penetration test is advisable for an Internet-facing remote-control product and its hosted service.

The explicit **no-go** behavior is important: if the selected profile's authenticated transport, strong authorization, media policy, or local enrollment isolation is unavailable, the application must disable remote admission and explain why. It must not offer an insecure automatic fallback or silently switch between profiles.

## Reference specifications for the proposed controls

- [GStreamer `webrtcbin` documentation](https://gstreamer.freedesktop.org/documentation/webrtc/) documents the ICE transport policy and TURN server controls; exact behavior still needs integration tests against the packaged version.
- [W3C WebAuthn Level 3](https://www.w3.org/TR/webauthn/) defines challenge/origin/RP-ID verification and credential backup flags. Backup eligibility is relevant to the distinction between an approved credential and a strictly device-bound credential.
- [Microsoft `New-NetFirewallRule` documentation](https://learn.microsoft.com/en-us/powershell/module/netsecurity/new-netfirewallrule) documents program/profile and `RemoteAddress` scoping, including `LocalSubnet`. Rule installation requires appropriate Windows privileges and is a supporting layer, not the app's only access check.
