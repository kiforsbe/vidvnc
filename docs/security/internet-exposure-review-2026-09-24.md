# Internet exposure security review — current implementation

> Superseded for branch `claude/remote-access-on-main` by the
> [2026-09-25 review](internet-exposure-review-2026-09-25.md), which covers the remote access
> mode and its media path.

Reviewed 2026-09-25 through `8308b55`. This is a source and regression review of the Windows host, Node HTTP/HTTPS and diagnostics servers, browser client, and native WebRTC worker. The primary assessment below assumes a competent operator satisfies the [Security-Related Application Conditions (SecRACs)](internet-exposure-remediation-proposals-2026-09-23.md); configuration failures are separated from defects that remain under that assumption. This is **not** an Internet penetration test or approval to expose the service remotely. The [2026-09-23 review](internet-exposure-review-2026-09-23.md) is a historical baseline. The [implementation status](internet-exposure-hardening-status-2026-09-24.md) records selected hardening; [remediation proposals](internet-exposure-remediation-proposals-2026-09-23.md) are options, not a selected remote deployment profile.

## Bottom line

**Under a correctly restricted external interface, no confirmed unauthenticated route to screen, input, owner management, or diagnostics was found.** A reachable HTTPS port `4383` exposes the public login shell/name and metered admission; admission still requires a valid host-issued code or approved-browser credentials. This is narrower than a claim that an administrator might accidentally publish local services. It is also **not yet a validated remote-desktop deployment**: HTTPS alone does not carry WebRTC media, an intentionally exposed direct media path has no app-defined remote network policy, and the approval UI has a misleading locality defect (F8). Binding `0.0.0.0` alone does not establish Internet reachability. [HTTPS bind](../../apps/server/src/tls/listener.mjs), [routes](../../apps/server/src/http-app.mjs), [WebRTC client](../../apps/web-client/src/stream-subscriptions.js).

**Primary threat-model assumptions:** The operator forwards only the intended HTTPS listener and, if remote media is required, a deliberately chosen and tested WebRTC path; preserves the actual client source IP; does not proxy the LAN HTTP/trust or loopback diagnostics listeners; uses a certificate trusted through a public CA or an independently verified fingerprint; conveys setup codes through an authenticated channel and verifies pending approvals; and supplies an appropriate public traffic edge. These are assumptions for this analysis, **not controls that VidVNC currently enforces or verifies end-to-end**. The project's [security policy](../../SECURITY.md) still describes a local-network development preview.

**Conditional configuration risks, outside this primary scenario:** A same-host proxy or NAT that makes an off-LAN client appear LAN-local can defeat _location checks_ for the standing password and trust page and collapse source-IP session binding (F1/F3). Installing the LAN HTTP-delivered anchor without independently checking its fingerprint permits on-path substitution (F3). Deliberately forwarding the separate diagnostics port removes its network isolation, although diagnostic API data still needs an owner-issued capability (F4). Explicit `tls.mode: off` serves plaintext LAN authentication. These remain important warnings, but should **not** be counted as vulnerabilities of the stipulated correctly configured external interface.

**What is already mitigated:** F1 short-code guessing/oracles are bounded; F2 removes revoked clients' HTTP access synchronously before native teardown; F3 keeps HTTP on eligible local addresses and refuses viewer/admission on unexpected TLS failure; F4 diagnostics is absent from public-capable ports; F7 caps admission work. No unauthenticated HTTP owner-management or approved-client approval path was found. These controls do **not** close the remaining rows above. A public hostname and TURN service are possible design choices, not universal prerequisites.

## Current exposure map

**Actual approved-interface exposure, in one sentence:** If `4383` is reachable with an accepted `Host`, outsiders can read the public login shell/name and try admission; a successfully admitted client can request protected viewer assets and session APIs, but media/input additionally needs a viable WebRTC path. The public JavaScript mentions some protected route names (for example `/viewer/` and `/api/disconnect`); those names are not secrets, but their code/data still require live authorization. Under the primary routing assumptions, local HTTP trust, private diagnostics, and owner-management commands are **not** externally exposed.

The default HTTPS bind is `0.0.0.0:4383`, meaning every IPv4 interface **if the host firewall and router allow connections**. Binding alone does not mean the PC is reachable from the Internet. The detailed surface inventory follows.

The main handler accepts loopback and current interface-IP `Host` values (including bracketed IPv6) and checks `Origin` when present. It does **not** require `Host` to match the interface actually reached: a raw client can choose an allowed header, and a non-browser client can omit `Origin`. Neither check authenticates the client. A same-host proxy can hide the original source IP, but is excluded from the primary scenario. **Even a correctly configured conventional NAT forward may fail:** if the router's public IP is not assigned to the host PC, a browser's public-IP `Host` is rejected with `403`; public DNS names are also rejected. This is a remote-setup compatibility defect, not an authentication bypass. ### Routes on a reachable HTTPS listener

- **Without a session, after an accepted `Host`:** `GET /`, `/app.js`, `/approved-client.js`, `/connection-link.js`, `/password-entry.js`, shared theme/style/shell files, `GET /api/info` returning exactly `{ "publicName": "…" }`, and the four admission endpoints: `/api/key-start`, `/api/approved-clients/register`, `/api/approved-clients/status`, and `/api/approved-clients/sign-in`. Public scripts necessarily reveal some post-admission route names, but not the viewer module or private host state. Codes and sign-in attempts are metered before secret lookup; seeing these routes is not approval to connect.
- **With a live viewer grant:** the fixed `/viewer/` fragment, JS, CSS, and helper-module routes. The grant cookie is `HttpOnly`, `SameSite=Strict`, path-limited to `/viewer`, and `Secure` on HTTPS; it is not an API bearer. The browser inserts the static fragment and imports the viewer module only after admission.
- **With a valid, source-IP-bound bearer:** session, stream, signaling, profile, and telemetry actions. These do not include approved-client management.
- **Denied even on the main HTTPS port:** an off-LAN peer gets `403` for `/trust`, its trust-specific assets, `/api/trust/status`, and `/api/trust/anchor`; the main handler returns `404` for diagnostics. There is no HTTP route for owner approval, permission changes, or removal.

A new approved browser/client credential still requires a host-issued setup code, one-use registration ticket, explicit owner approval, and a one-time claim token. The local-only anchor endpoint serves **public certificate bytes**, never the private key. Its risk is authenticity: a LAN attacker can replace an HTTP-delivered certificate unless the installer checks its actual fingerprint independently against the host. [Admission and static routes](../../apps/server/src/http-app.mjs), [registration](../../apps/server/src/approved-clients.mjs), [certificate strategy](../../apps/server/src/tls/strategies/mkcert.mjs).

**Certificate identity still leaks separately from the page.** The automatically provisioned certificate can list the machine hostname and discovered interface IPs in its Subject Alternative Names. A TLS peer that can reach the listener can inspect that public certificate even though `/api/info` and the login HTML no longer disclose those details. A provided certificate has its own operator-chosen identity. [Certificate address collection](../../apps/server/src/tls/local-addresses.mjs).

### F8 — pending remote approval can be labeled “Local network” (unmitigated)

Production creates one HTTP handler for both narrow local HTTP and public-capable HTTPS, leaving its `listenerScope` at the default `local`. During registration it sets the pending request's `network` label from that handler setting rather than the request's actual peer address. The Windows host displays the label next to the approval buttons. Therefore an off-LAN HTTPS registrant **with a valid host-issued setup code/ticket** can appear as “Local network” to the owner. They still cannot approve themselves or obtain a credential without the owner action; this is a misleading security cue, not an authentication bypass. Client/browser names are also supplied by the registrant and must not be treated as verified device identity. [Shared handler](../../apps/server/src/server-http-stack.mjs), [registration label](../../apps/server/src/http-app.mjs), [owner UI](../../apps/windows-host/HostWindow.Clients.cs).

**Needed before relying on the approval UI for remote enrollment:** under direct routing, derive any locality claim from the actual socket peer; if that cannot be established, display “Network not verified.” A future proxy mode would need an explicit trusted-proxy policy. Add a production-stack regression for an off-LAN HTTPS registration. This review documents the defect; it does not implement that fix.

**Viewer-asset bypass check:** `/viewer/` routes use a fixed file map, reject absent/duplicate/malformed grants with `404`, bind grants to the live session and socket IP, and check again after file reads. Session revocation removes the grant synchronously. A cookie alone cannot call `/api/profiles`, `/api/offer`, or stream/input endpoints; those still require a bearer. A stolen viewer cookie from the same apparent source (including clients collapsed behind a proxy) could read viewer code while its session lives, but would not gain media access from the cookie alone. Previously downloaded client code cannot be erased from a client. These are disclosure and replay limits, not a substitute for transport/origin policy. [Grant](../../apps/server/src/viewer-asset-grants.mjs), [router](../../apps/server/src/http-app.mjs), [race regression](../../apps/server/tests/http-security.test.mjs).

The approved browser/client secret is also readable by same-origin browser code after enrollment. The current pages use a restrictive CSP, fixed self-hosted assets, and no ambient **API** session cookie; the new viewer cookie is intentionally asset-only. A compromised HTTPS origin, malicious extension, or local browser compromise can still copy the IndexedDB secret. This is a consequence of the selected client-secret model, **not** a confirmed XSS finding. [Browser storage](../../apps/web-client/src/approved-client.js), [CSP](../../apps/server/src/http-app.mjs).

## Deployment consequences and release gates

- **Only HTTPS is exposed, as assumed:** anonymous access remains the login/name and metered admission surface, not private viewer or management data. Application HTTP routes fail closed when required TLS fails. A self-signed certificate must already be trusted through independently verified identity; the LAN HTTP trust page is not a remote enrollment mechanism. Sign-in can work, but screen/audio/input still needs a separate viable ICE path. F8 can mislabel a valid remote registration.
- **HTTPS plus deliberately permitted direct WebRTC:** this may provide remote media if topology allows, without TURN, but the application has no supported fixed UDP/candidate/egress policy. Specify and test the exact firewall/ICE behavior and native worker exposure on IPv4 and IPv6. If a relay is selected instead, configure short-lived authenticated TURN and enforce its candidate policy; TURN is not universally required.
- **HTTP or local-only services forwarded outside the assumptions:** the HTTP listener binds only loopback and eligible Private LAN addresses, and diagnostics is separate and loopback-only. A same-host proxy/NAT can nevertheless make remote requests look local; deliberate `tls.mode: off` can expose plaintext authentication. These are misconfiguration/topology risks, not demonstrated exposure in the primary scenario. Do not treat arbitrary forwarding headers as proof of client identity.

Before a **product-supported remote-ready claim**, fix the public `Host` compatibility issue and F8's false locality label; select and validate an intentional WebRTC topology (F6), including the native worker and firewall path; explicitly accept or replace the copyable approved-browser credential model (F5); and exercise native revocation, hardware media, TLS identity/failure, edge limits, and real-network behavior. A public hostname and TURN service are topology-dependent options, not universal prerequisites. An opt-in remote mode, app-managed firewall preflight, and proxy-aware configuration would help enforce and report the SecRACs, but their absence is **not by itself proof of an authorization bypass** in the correctly configured primary scenario. The [security policy](../../SECURITY.md) still limits this development preview to trusted local networks; this review does not change that support position.

**Compatibility issue, not an authentication bypass:** the handler's accepted `Host` values are loopback or current interface IPs. A configured public-DNS URL can be advertised but rejected with `403`; a public-IP URL forwarded by an ordinary NAT router is likewise rejected when that public IP is not assigned to the host PC. A raw client can supply an accepted `Host` header, so this guard is not authentication. It must be resolved for those legitimate public origins, but is distinct from the security findings above. [Host guard](../../apps/server/src/http-app.mjs), [address selection](../../apps/server/src/tls/addresses.mjs).
