# Internet exposure security review — current implementation

Reviewed 2026-09-25 through `e2244db`, including the preceding Host, IPv6, and advertised-address fixes and the new public-login/viewer boundary. This is a source and regression review of the Windows host, Node HTTP/HTTPS and diagnostics servers, browser client, and native WebRTC worker. The [2026-09-23 review](internet-exposure-review-2026-09-23.md) is a historical baseline. The [implementation status](internet-exposure-hardening-status-2026-09-24.md) records verification and residuals; [remediation proposals](internet-exposure-remediation-proposals-2026-09-23.md) are not a selected remote deployment profile.

## Why Internet exposure is still blocked

**The central gap is that VidVNC has no defined, enforced remote-access boundary.** HTTPS protects login and signaling, but the screen, audio, and input stream uses separate WebRTC connections. There is no selected or enforced remote ICE, UDP-port, firewall, or direct/relay policy (F6). Forwarding HTTPS alone may allow login without a working stream; opening UDP broadly would expose the native media/input stack without a reviewed network boundary.

Other conditions must also be resolved for a remote deployment:

- **“Local-only” can be defeated by a same-host proxy.** A remote client forwarded through loopback can appear local to standing-password and trust-enrollment checks, and different clients can appear to share one source IP. No supported proxy/source-address policy or remote-mode preflight prevents this (F1/F3).
- **Remote certificate enrollment is not established.** The trust page is deliberately LAN-only, and its HTTP certificate download is not authentic unless the user verifies the actual fingerprint independently against the host. Public DNS/origin handling is also unfinished; a configured DNS-name URL can be advertised yet rejected by the `Host` guard (F3).
- **An approved client is not a physical-device identity.** Its browser-held secret is copyable. One-live-session and revocation controls help, but a remote deployment must explicitly accept this credential model or replace it (F5). In-process attempt limits also do not replace an Internet edge or real-network load testing (F7).

The recent work **did** narrow F1 key guessing, make server-side revocation immediate for new requests (F2), restrict HTTP to eligible LAN addresses and fail closed when required HTTPS fails (F3), isolate diagnostics from the public-capable ports (F4), and bound admission work (F7). Those fixes do not make the current listeners Internet-ready. **Do not port-forward them as a remote-access setup.** A remote-ready claim needs a chosen, tested WebRTC network path and an explicit origin/TLS/enrollment, proxy/source, firewall, and edge policy. A public hostname or TURN service may be part of that design, but neither is a universal prerequisite.

## Current exposure map

**Potential exposure:** If HTTPS port `4383` is reachable, outsiders can see the login page and chosen public name and try admission. Viewer assets require a live session grant; private APIs require a separate bearer. HTTP trust, diagnostics, and owner management are not directly exposed. WebRTC media/input uses separate sockets without a defined remote network policy (F6).

The default HTTPS bind is `0.0.0.0:4383`, meaning every IPv4 interface **if the host firewall and router allow connections**. Binding alone does not mean the PC is reachable from the Internet. The detailed surface inventory follows.

| Surface | Can a direct off-LAN client reach it? | What is exposed or still at risk |
| --- | --- | --- |
| Main HTTP (`4382`) | **No public bind.** Loopback and eligible Private LAN addresses only. | With required TLS, local trust routes and three shared assets remain; viewer/API routes redirect or return `503`. Explicit `tls.mode: off` serves the full LAN viewer in plaintext. |
| Main HTTPS (`4383`) | **Potentially yes.** Default bind is all IPv4 interfaces when TLS is active; firewall/NAT decides actual Internet reachability. | Public login shell, shared theme/styles, one-field `/api/info`, and four admission endpoints need no session. The owner-chosen name is public. This is **not** a supported remote mode. |
| Viewer assets | **Only after admission.** HTTPS for off-LAN; deliberate TLS-off LAN HTTP also serves them. | `/viewer/fragment.html`, `/viewer/app.js`, `/viewer/style.css`, and four stream helpers require a live, source-IP-bound, session-linked `HttpOnly` viewer cookie. Revocation denies new asset requests; a read in progress rechecks before sending bytes. The cookie cannot authorize APIs. |
| Session/signaling API | **Potentially yes, through HTTPS after admission.** | Requires a separate current bearer tied to the socket source IP. Stream selection can enable control under host policy; it cannot edit owner policy. |
| Trust page and APIs | **No direct off-LAN access.** HTTPS returns `403`; HTTP has no public bind. | Local peers can fetch public certificate/status. A same-host proxy can make remote traffic look local; LAN HTTP certificate delivery needs independent fingerprint verification. |
| Diagnostics | **No on main ports:** `404`. Separate OS-assigned `127.0.0.1` port only. | Private API needs an owner-issued bearer. A manually configured proxy to that private port would defeat network isolation. |
| WebRTC media/input | **Potentially, after stream admission,** on separate dynamic ICE sockets. Reachability depends on the network. | Carries DTLS/SRTP media and an input data channel outside HTTPS. No selected remote ICE/UDP/firewall policy (F6). |
| Owner management | **No HTTP administration route.** | Approval, permission edits, removal, and diagnostics-capability issuance use local CLI/Windows-host commands. |

The main handler accepts loopback and current interface-IP `Host` values (including bracketed IPv6) and checks `Origin` when present. It does **not** require `Host` to match the interface actually reached: a raw client can choose an allowed header, and a non-browser client can omit `Origin`. Neither check authenticates the client. A same-host proxy can also hide the original source IP. A DNS-name bind can be advertised but rejected by the IP-only `Host` guard. [HTTP routing](../../apps/server/src/http-app.mjs), [listeners](../../apps/server/src/lan-http-listeners.mjs), [TLS bind](../../apps/server/src/tls/listener.mjs), [WebRTC peer](../../apps/web-client/src/stream-subscriptions.js), [diagnostics](../../apps/server/src/diagnostics-http.mjs).

### Routes on a reachable HTTPS listener

- **Without a session, after an accepted `Host`:** `GET /`, public admission scripts and shared theme/style/shell files, `GET /api/info` returning exactly `{ "publicName": "…" }`, and the four admission endpoints: `/api/key-start`, `/api/approved-clients/register`, `/api/approved-clients/status`, and `/api/approved-clients/sign-in`. Codes and sign-in attempts are metered before secret lookup; seeing these routes is not approval to connect.
- **With a live viewer grant:** the fixed `/viewer/` fragment, JS, CSS, and helper-module routes. The grant cookie is `HttpOnly`, `SameSite=Strict`, path-limited to `/viewer`, and `Secure` on HTTPS; it is not an API bearer. The browser inserts the static fragment and imports the viewer module only after admission.
- **With a valid, source-IP-bound bearer:** session, stream, signaling, profile, and telemetry actions. These do not include approved-client management.
- **Denied even on the main HTTPS port:** an off-LAN peer gets `403` for `/trust`, its trust-specific assets, `/api/trust/status`, and `/api/trust/anchor`; the main handler returns `404` for diagnostics. There is no HTTP route for owner approval, permission changes, or removal.

A new approved browser/client credential still requires a host-issued setup code, one-use registration ticket, explicit owner approval, and a one-time claim token. The local-only anchor endpoint serves **public certificate bytes**, never the private key. Its risk is authenticity: a LAN attacker can replace an HTTP-delivered certificate unless the installer checks its actual fingerprint independently against the host. [Admission and static routes](../../apps/server/src/http-app.mjs), [registration](../../apps/server/src/approved-clients.mjs), [certificate strategy](../../apps/server/src/tls/strategies/mkcert.mjs).

**Certificate identity still leaks separately from the page.** The automatically provisioned certificate can list the machine hostname and discovered interface IPs in its Subject Alternative Names. A TLS peer that can reach the listener can inspect that public certificate even though `/api/info` and the login HTML no longer disclose those details. A provided certificate has its own operator-chosen identity. [Certificate address collection](../../apps/server/src/tls/local-addresses.mjs).

### Changes since the preceding review

- `4cb1363` replaced the startup snapshot of permitted `Host` values with a live interface check, including bracketed IPv6, so adapter changes no longer strand an otherwise eligible LAN viewer. It split trust-only paths from three shared static assets: `/theme.js`, `/style.css`, and `/shell.css` are now accessible to off-LAN clients on an active HTTPS listener because the normal viewer loads them; `/trust`, trust-specific assets, and trust APIs remain local-only. The shared files contain client-side presentation code, not an owner capability. [Handler](../../apps/server/src/http-app.mjs), [regressions](../../apps/server/tests/http-security.test.mjs).
- `ed31b8d` constrains advertised HTTPS addresses to the listener's selected IP family. The default `0.0.0.0` bind advertises IPv4 only; an IPv6 bind advertises bracketed IPv6 and uses `::1` for local preview when appropriate. This fixes misleading connection instructions, but does not constrain the HTTPS bind to a Private LAN, validate certificate names, or create a supported public-DNS setup. [Address selection](../../apps/server/src/tls/addresses.mjs), [regressions](../../apps/server/tests/tls/addresses.test.mjs).
- `1148c6e` made `/api/info` one-field public metadata and added `public-name`; `abd7a75`, `a10cc7f`, and `e2244db` introduced revocable viewer grants, protected `/viewer/` assets, and a public admission shell that loads the viewer only after success. The old anonymous root stream-helper URLs now return `404`. These changes reduce pre-login page disclosure, not F6 or the remote deployment risk. [Public shell](../../apps/web-client/src/app.js), [protected viewer](../../apps/web-client/src/viewer/app.js), [route gate](../../apps/server/src/http-app.mjs).

These commits do not make a remote deployment ready. In particular, viewer-gating does not alter approved-client assurance, local trust enrollment, same-host proxy behavior, or WebRTC transport. The anonymous HTTPS asset set is now the admission shell and its shared styles/scripts, not viewer-specific modules or trust-specific paths.

**Viewer-asset bypass check:** `/viewer/` routes use a fixed file map, reject absent/duplicate/malformed grants with `404`, bind grants to the live session and socket IP, and check again after file reads. Session revocation removes the grant synchronously. A cookie alone cannot call `/api/profiles`, `/api/offer`, or stream/input endpoints; those still require a bearer. A stolen viewer cookie from the same apparent source (including clients collapsed behind a proxy) could read viewer code while its session lives, but would not gain media access from the cookie alone. Previously downloaded client code cannot be erased from a client. These are disclosure and replay limits, not a substitute for transport/origin policy. [Grant](../../apps/server/src/viewer-asset-grants.mjs), [router](../../apps/server/src/http-app.mjs), [race regression](../../apps/server/tests/http-security.test.mjs).

The approved browser/client secret is also readable by same-origin browser code after enrollment. The current pages use a restrictive CSP, fixed self-hosted assets, and no ambient **API** session cookie; the new viewer cookie is intentionally asset-only. A compromised HTTPS origin, malicious extension, or local browser compromise can still copy the IndexedDB secret. This is a consequence of the selected client-secret model, **not** a confirmed XSS finding. [Browser storage](../../apps/web-client/src/approved-client.js), [CSP](../../apps/server/src/http-app.mjs).

## Deployment consequences and release gates

- **Forward only HTTPS:** application HTTP routes now fail closed when required TLS fails, but a public HTTPS listener is still not a supported remote deployment. A self-signed certificate needs independent fingerprint verification at installation; the LAN HTTP trust page is not remote enrollment. Public Host/origin, approved-client assurance, and WebRTC policy remain to be specified and tested.
- **Forward HTTP and HTTPS:** HTTP listener binding is narrowed to loopback and eligible Private LAN addresses, so an ordinary Internet port forward has no supported public HTTP listener. Do not use a same-host proxy or NAT rule to turn the local trust/explicit-off HTTP surface into a public service; such forwarding can launder source addresses and, in deliberate `off`, expose plaintext authentication.
- **Reverse proxy to loopback:** unsupported as a remote-access shortcut. Its backend socket appears local, potentially bypassing standing-password and trust-locality checks; it also collapses session IP binding. Never proxy the diagnostics port. Do not trust arbitrary forwarded headers.
- **Direct WebRTC:** a working signaling connection is insufficient. Define which ICE candidates, remote addresses, UDP ports, and firewall paths are intended; then test on the chosen topology. If a relay is selected, provision short-lived authenticated TURN and enforce the intended candidate policy. If no relay is selected, document and test the narrower direct/VPN topology and its reliability/security tradeoffs.

Before a remote-ready claim, select an explicit opt-in remote deployment policy and test its public-origin/Host, HTTPS certificate and trust-enrollment, source-address/proxy, firewall, and failure states. F1's live LAN scope and F3's local HTTP/fail-closed request paths are now implemented, but they do not solve same-host proxy laundering or supply remote enrollment. Independently select and validate a WebRTC network policy (F6), explicitly accept or replace the copyable approved-browser credential model (F5), exercise native revocation and hardware media, and perform real-network TLS, firewall, load, and penetration tests. A public hostname and TURN service are topology-dependent options, not universal prerequisites.

## Verification and limits of this review

For this review through `e2244db`, `npm test` passed **816/816**, and `npm run format:check`, `npm run test:host`, `node apps/server/tests/runtime-start-check.mjs`, and `dotnet build apps/windows-host/VidVnc.Host.csproj --no-restore` passed. Real Chromium fixtures passed for key and approved-client sign-in, legacy and subscription WebRTC, viewer controls, reconnect, disconnect/re-login, and narrow/mobile layout. Live loopback route regressions exercised anonymous `/`, one-field `/api/info`, protected viewer assets, cookie-only API denial, grant revocation during a file read, LAN HTTP, required-HTTPS failure, and `Secure` viewer cookies on a real HTTPS listener. A prior local probe confirmed the DNS-name configuration mismatch: address selection advertised `https://example.test:4383`, while the handler answered `403` for that hostname on loopback; it was not rerun here. The earlier Windows navigation regression and `npm audit --omit=dev --json` were also not rerun. These checks use injected adapters for several network cases and do not scan GStreamer/native dependencies or prove live Internet security. No external penetration test, physical IPv6/adapter-transition test, physical host-button test, hardware WebRTC run, packet-level ICE egress test, public TLS scan, or Internet deployment was performed.
