# Internet exposure security review — current implementation

Reviewed 2026-09-24 against commits through `693b50b` (F1/F3 implementation plus the earlier F2/F4/F5/F7 hardening). This is a source and regression review of the Windows host, Node HTTP/HTTPS and diagnostics servers, browser client, and native WebRTC worker. The [2026-09-23 review](internet-exposure-review-2026-09-23.md) is a historical baseline. The [implementation status](internet-exposure-hardening-status-2026-09-24.md) records verification and residuals; [remediation proposals](internet-exposure-remediation-proposals-2026-09-23.md) are not a selected remote deployment profile.

## Decision

**Do not expose the current listeners directly to the Internet.** F1's live LAN-scope wiring is now corrected. F3's application-level paths now fail closed: HTTP binds only loopback and eligible Private-LAN interface addresses, rejects out-of-scope peers, redirects viewer/API traffic only while HTTPS is active, and denies viewer/API admission when required HTTPS is unavailable. Valid, deliberate `tls.mode: off` still serves the full viewer over LAN-only HTTP. Trust enrollment is restricted to local-scope peers on HTTP and HTTPS, and absolute-form request targets are validated before routing. This narrows F3 in code but does **not** authorize Internet exposure: the HTTPS listener may still be public under `VIDVNC_HOST`, F6 has no selected remote ICE/firewall policy, and there is no remote-mode preflight or deployment validation.

The reviewed design treats an approved browser/client secret as an **additional copyable credential** alongside username and password. It does not prove possession of a physical device. One-live-session and revocation controls limit reuse but do not turn it into a device credential.

### HTTPS-reachable sub-pages and endpoints

The main HTTPS port exposes the anonymous viewer, its exact static asset list, `/api/info`, and the four anonymous admission endpoints. `/trust`, its trust-specific assets, and trust metadata/download are available only to local-scope peers on either scheme; shared theme/style/shell assets remain available to the viewer. A visitor can read client-side code and service metadata without logging in; that is not itself an authorization bypass. `/api/key-start` distinguishes success from failure, but attempts are metered **before** key lookup and the code no longer reveals its purpose through an inspection endpoint. Approved registration still requires a host-issued setup code, a one-use registration ticket, and explicit owner approval before a claimant can retrieve the client secret. The resulting secret is delivered once through a high-entropy claim token. [Key start and routes](../../apps/server/src/http-app.mjs), [registration](../../apps/server/src/approved-clients.mjs).

`/api/trust/anchor` returns only public certificate bytes, not the host private key. Its remaining security problem is **authenticity of what a user installs**: local HTTP delivery can be replaced on path unless the certificate's actual fingerprint is checked genuinely out of band against the host. Installing a `mkcert` root grants trust beyond one leaf certificate. The trust page and anchor are local enrollment surfaces, not a safe Internet bootstrap. [Trust routes](../../apps/server/src/http-app.mjs), [certificate strategy](../../apps/server/src/tls/strategies/mkcert.mjs).

Claim status needs an unguessable token and releases the secret once, before the ten-minute claim window ends. An attacker with a stolen live setup code or ticket can submit a request, but not approve it through HTTP. | Bypass approved-only mode with an ordinary key             | New ordinary key admissions check the mode. [Approved store](../../apps/server/src/approved-clients.mjs), [browser storage](../../apps/web-client/src/approved-client.js).                                                                                                                                                                                                                            |
| Reuse a session bearer elsewhere                           | Session IDs are random UUID bearers and must match the source socket IP. This is a partial friction layer, not device binding; a same-host reverse proxy collapses different remote clients to its backend IP, and a bearer leak behind that proxy can be replayed from the same apparent source. Browser sessions are held in JS memory rather than cookies, so there is no ambient cookie-authenticated API. [Session store](../../apps/server/src/session-store.mjs), [router](../../apps/server/src/http-app.mjs), [browser client](../../apps/web-client/src/app.js).                          |

The approved browser/client secret is also readable by same-origin browser code after enrollment. The current pages use a restrictive CSP, fixed self-hosted assets, and no ambient session cookie, but a compromised HTTPS origin, malicious extension, or local browser compromise can still copy the IndexedDB secret. This is a consequence of the selected client-secret model, **not** a confirmed XSS finding. [Browser storage](../../apps/web-client/src/approved-client.js), [CSP](../../apps/server/src/http-app.mjs).

## Deployment consequences and release gates

- **Forward only HTTPS:** application HTTP routes now fail closed when required TLS fails, but a public HTTPS listener is still not a supported remote deployment. A self-signed certificate needs independent fingerprint verification at installation; the LAN HTTP trust page is not remote enrollment. Public Host/origin, approved-client assurance, and WebRTC policy remain to be specified and tested.
- **Forward HTTP and HTTPS:** HTTP listener binding is narrowed to loopback and eligible Private LAN addresses, so an ordinary Internet port forward has no supported public HTTP listener. Do not use a same-host proxy or NAT rule to turn the local trust/explicit-off HTTP surface into a public service; such forwarding can launder source addresses and, in deliberate `off`, expose plaintext authentication.
- **Reverse proxy to loopback:** unsupported as a remote-access shortcut. Its backend socket appears local, potentially bypassing standing-password and trust-locality checks; it also collapses session IP binding. Never proxy the diagnostics port. Do not trust arbitrary forwarded headers.
- **Direct WebRTC:** a working signaling connection is insufficient. Define which ICE candidates, remote addresses, UDP ports, and firewall paths are intended; then test on the chosen topology. If a relay is selected, provision short-lived authenticated TURN and enforce the intended candidate policy. If no relay is selected, document and test the narrower direct/VPN topology and its reliability/security tradeoffs.

Before a remote-ready claim, select an explicit opt-in remote deployment policy and test its public-origin/Host, HTTPS certificate and trust-enrollment, source-address/proxy, firewall, and failure states. F1's live LAN scope and F3's local HTTP/fail-closed request paths are now implemented, but they do not solve same-host proxy laundering or supply remote enrollment. Independently select and validate a WebRTC network policy (F6), explicitly accept or replace the copyable approved-browser credential model (F5), exercise native revocation and hardware media, and perform real-network TLS, firewall, load, and penetration tests. A public hostname and TURN service are topology-dependent options, not universal prerequisites.

## Verification and limits of this review

On this checkout, `npm test` passed **805/805**, `npm run format:check`, `npm run test:host`, `node apps/server/tests/runtime-start-check.mjs`, the WinUI host build, and the Windows navigation regression passed. Tests include narrow HTTP binds/reconciliation, dynamic IPv4/IPv6 Host and live-scope routing, shared HTTPS viewer assets, absolute-form targets, TLS-unavailable `503`, local-only trust routes, and viewer/trust address separation. The earlier `npm audit --omit=dev --json` reported zero production Node advisories; it was not rerun for this update. These checks do not scan GStreamer/native dependencies or prove live Internet security. No external penetration test, physical host-button test, hardware WebRTC run, packet-level ICE egress test, public TLS scan, or Internet deployment was performed.
