# Internet exposure security review

For concrete code/configuration changes, acceptance tests, and Security-Related Application Conditions (SecRAC) for each finding, see the [remediation proposals](internet-exposure-remediation-proposals-2026-09-23.md). The owner subsequently approved a [focused design for F1, F2, F4, F5, and F7](../superpowers/specs/2026-09-23-selected-internet-exposure-hardening-design.md); that document tracks what the selected work would address and what remains open. It is a design, **not an implemented mitigation or an Internet-release approval**.

Reviewed 2026-09-23 against commit `35e37d8` (`0.8.0`). This is a source review of the Windows host, Node server, browser client, and native media worker. It includes targeted local reproductions, the portable test suite, and the Node dependency audit. It does not include an external penetration test, live Internet deployment, hardware WebRTC test, native dependency vulnerability scan, or TLS configuration scan.

## Decision

Do not publish the current service directly to the Internet. HTTPS encrypts the signaling connection when its listener is healthy, but it does not make the existing LAN authentication, enrollment, control authorization, or direct WebRTC transport suitable for remote use. The most urgent code findings are an unthrottled online connection-key oracle and a live `view-only` control bypass. The transport and certificate enrollment design also need a distinct remote mode.

The risk depends on deployment. Forwarding **only** the HTTPS port avoids exposing the plaintext listener to the Internet, but a TLS failure then makes the remote service unavailable. Forwarding both listeners exposes plaintext enrollment and, if TLS fails, the full application over HTTP. A reverse proxy introduces a different set of origin and loopback-trust problems described below.

### What the browser can reach before signing in

The main and trust pages, their static code/styles, `/api/info`, and the trust status/anchor endpoints are anonymous. The connection-key inspection endpoint is also anonymous and reveals whether a submitted key is valid and its purpose. Registration submission requires a valid setup key; obtaining approved credentials still requires host approval. A registration claimant uses an unguessable claim token to poll status and receive the approved secret once. An approved client then signs in with client ID, client secret, username, and password. Ordinary clients submit a session or one-time key. [HTTP flow](../../apps/server/src/http-app.mjs#L401), [registration store](../../apps/server/src/approved-clients.mjs#L102).

### What an authenticated client can do

A session bearer permits reading the permitted profile/display catalog, creating video/audio subscriptions, selecting a stream, sending telemetry, and ending its own streams/session. Stream IDs are checked against the bearer before stop/telemetry operations. A session can view the desktop and, when host policy grants a control lease, use the native WebRTC input channel. There is no HTTP API to list other approved clients, change access settings, or grant another session control. [Session routes](../../apps/server/src/http-app.mjs#L501), [stream ownership](../../apps/server/src/stream-registry.mjs#L145), [control lease](../../apps/server/src/control-lease.mjs#L31).

## Confirmed findings

### F1 — High: online connection-key guesses bypass the intended rate limit

`/api/connection-key` calls `keys.inspect()` and returns 200 with purpose/usage/expiry for a valid key. It has no attempt accounting. `/api/connect` also calls `keys.inspect()` **before** `SessionStore.connect()`, returning 401 for an incorrect guess; `SessionStore.connect()` is where the five-attempts-per-minute source limiter lives. Thus invalid HTTP guesses never enter that limiter. [Inspection route](../../apps/server/src/http-app.mjs#L401), [connect route](../../apps/server/src/http-app.mjs#L477), [limiter](../../apps/server/src/session-store.mjs#L65).

The key format has 24 possible letters, six first letters per purpose, and seven further letters: `6 × 24^7 = 27,518,828,544` possibilities, about 34.68 bits for a chosen purpose. Session keys do not expire during an instance; setup and one-time keys default to ten minutes. The oracle makes a successful guess distinguishable even when all session slots are occupied. [Generation and lifetime](../../apps/server/src/connection-keys.mjs#L34).

**Local reproduction:** eight bad `/api/connect` requests all returned 401, then the valid key still returned 201. Eight bad `/api/connection-key` calls likewise returned 401, with no throttling response. This does not measure feasible request throughput, but it proves the intended server-side attempt budget is not enforced at these HTTP entry points.

**Impact:** a successful session-key guess yields desktop viewing, and may yield keyboard/mouse control under the host's `available` policy. Guessing a setup key permits registration submission; host approval remains necessary before receiving the approved credential. Short-lived one-time keys reduce exposure time but retain the same online oracle.

**Fix:** remove or strictly limit the inspection oracle; account for **every** attempted key before lookup, including malformed or unknown keys; apply a server-wide budget as well as source budgets; and use a much higher-entropy capability for remote access/enrollment. Test HTTP endpoints, not only `SessionStore.connect()`.

### F2 — High: `view-only` changes do not revoke or prevent captured automatic control

At admission, `StreamRuntime` reads an approved client's permission once. If it is `available`, it adds the session to `automaticControl`. On stream selection, that set is consumed and `ControlLease.grant()` runs without re-reading current approved-client permission. The manual host `grant` command does check `view-only`, but the automatic path does not. Separately, the host's permission-change command only persists the new value; it does not revoke an existing lease. Renewal every two seconds checks active stream/session state, not current permission. [Admission and selection](../../apps/server/src/stream-runtime.mjs#L37), [manual check](../../apps/server/src/stream-runtime.mjs#L121), [permission update](../../apps/server/src/main.mjs#L345), [renewal](../../apps/server/src/main.mjs#L218).

**Local reproduction:** construct a session while its approved-client permission is `available`, change the permission source to `view-only`, then select its live stream. `runtime.control.owner` becomes that session despite the current `view-only` value. If control was already held when permission changes, the lease can continue to renew.

**Impact:** the host's visible “View only” setting is not an immediate or complete control boundary for a connected client. This matters especially when the remote client is no longer trusted.

**Fix:** make permission changes transactional with revocation of affected live leases and cancellation of pending automatic grants. Check the current effective permission in the grant path and during renewal. Add tests for a change before first selection, during active control, and during an in-flight grant.

### F3 — High, deployment dependent: HTTPS can degrade to full HTTP, and enrollment remains plaintext

The plaintext listener binds first and remains running. Bad TLS settings, certificate provisioning failure, or HTTPS bind failure leave the service serving plaintext. When HTTPS is healthy, `/trust`, its assets, `/api/trust/status`, and `/api/trust/anchor` stay on HTTP by design. The redirect also applies only when the raw HTTP request target starts with `/`. Node accepts an absolute-form target such as `http://127.0.0.1:4382/api/connect`; the router extracts `/api/connect` and processes it on HTTP without redirecting. [Startup](../../apps/server/src/main.mjs#L501), [settings fallback](../../apps/server/src/tls/load-settings.mjs#L32), [listener fallback](../../apps/server/src/tls/listener.mjs#L149), [redirect condition](../../apps/server/src/http-app.mjs#L234), [allowlist](../../apps/server/src/http-app.mjs#L40).

**Local reproduction of the redirect bypass:** with a stub reporting HTTPS active, an origin-form `POST /api/connect` returned 307, while an absolute-form `POST http://127.0.0.1:<port>/api/connect` with the same valid key returned 201 on the plaintext socket. Ordinary browsers generally send origin-form targets to an origin server, so this is primarily a nonbrowser/proxy path; it confirms that the server does not enforce HTTPS for sensitive API requests.

If the operator forwards both ports, an HTTPS failure exposes passwords/keys and bearer sessions over HTTP. Even while HTTPS works, an on-path attacker can tamper with the HTTP trust page or substitute the downloaded anchor. The UI asks users to compare the fingerprint with the host, which helps only when that comparison is genuinely out of band. A public remote deployment should not depend on unauthenticated HTTP certificate enrollment. In `mkcert` mode, installing the offered root also grants trust broader than one VidVNC leaf certificate. [Anchor response](../../apps/server/src/http-app.mjs#L336), [mkcert anchor](../../apps/server/src/tls/strategies/mkcert.mjs#L110).

**Fix:** add an explicit remote mode that requires a valid operator-provided/public certificate, fails startup or disables remote admission when TLS is unavailable, and does not expose the plaintext listener or trust-anchor enrollment publicly. On any remaining HTTP listener, reject sensitive API operations based on the actual socket security state for every request-target form. Use firewall rules as an independent check.

### F4 — Medium, deployment dependent: a loopback reverse proxy can expose diagnostics

Diagnostics access is decided from `request.socket.remoteAddress` and `Host`, with no login. A reverse proxy on the same machine that forwards to the HTTPS backend at `127.0.0.1` and rewrites `Host` to `localhost` makes an Internet request look exactly like an allowed local request. The same applies to an HTTP backend when TLS is inactive. `/api/diagnostics` then exposes stream labels and runtime measurements, including connected-device/address metadata. An HTTP backend with TLS active would redirect this path before the diagnostics check. [Guard and response](../../apps/server/src/http-app.mjs#L246), [labels](../../apps/server/src/stream-runtime.mjs#L171).

A proxy that preserves the public `Host` does not produce this specific leak, but the current host allowlist and origin comparison then reject a public DNS name or HTTPS `Origin` forwarded over HTTP. The service therefore needs explicit proxy trust and a separate authentication boundary for diagnostics before this deployment style is supported. [Host guard](../../apps/server/src/http-app.mjs#L213), [origin check](../../apps/server/src/tls/origin.mjs#L27).

**Fix:** bind diagnostics to a separate loopback-only management listener, or require a host-only credential independent of forwarded network headers. Configure public origins explicitly and accept forwarding headers only from named trusted proxies.

### F5 — Medium: an “approved device” credential is copyable and supports multiple sessions

The browser saves client ID, client secret, and username in IndexedDB. The user's password is entered at sign-in. `installationId` is recorded as registration metadata but not checked at authentication. A copy of the saved credential plus the password can sign in from another device, and the server does not enforce one active session per approved-client ID. [Browser storage](../../apps/web-client/src/approved-client.js#L1), [registration/authentication](../../apps/server/src/approved-clients.mjs#L102), [approved admission](../../apps/server/src/session-store.mjs#L95).

This is not a passwordless bypass: the attacker still needs the password and high-entropy client secret. It does mean that “approved client” is a transferable credential rather than a cryptographically bound device identity. IP binding of a later session bearer does not address credential cloning, and collapses to the proxy's IP behind a reverse proxy.

**Fix:** for remote use, enroll a device-held private key or passkey, verify a challenge at sign-in, show concurrent sessions per approved client, and allow the host to revoke every session for that identity.

### F6 — Medium: direct WebRTC exposure is separate from HTTPS and lacks a remote network policy

The browser uses `RTCPeerConnection({ iceServers: [] })`; the server hands caller-provided SDP (up to 65,536 characters, prefixed by `v=0`) to the native GStreamer peer. There is no application-level ICE candidate allowlist, TURN credential issuance, fixed port range, or relay-only policy. GStreamer/libnice opens the ICE transport sockets; the encrypted media and input channel then traverse those sockets, independently of HTTPS. [Browser configuration](../../apps/web-client/src/stream-subscriptions.js#L59), [signaling check](../../apps/server/src/http-app.mjs#L518), [native SDP processing](../../native/media-worker/src/media-worker.cpp#L1192).

Simply forwarding TCP 4383 will generally not make remote media connect; a direct public UDP path would expose the native ICE/DTLS/SRTP stack. Since an authenticated client controls SDP candidate text, candidate-directed ICE checks to internal or otherwise unintended UDP destinations are a plausible egress/probing concern. That concern has **not** been experimentally confirmed here; libnice behavior and firewall policy need a dedicated test. An unauthenticated Internet packet may still reach a directly exposed ICE socket if the firewall permits it, even though completing a peer connection requires signaling credentials.

**Fix:** design remote media around an authenticated TURN relay with short-lived per-session credentials and relay-only candidate policy; restrict host egress/ingress to the relay; pin and audit the native media dependencies; fuzz SDP and ICE inputs and test the actual network behavior.

### F7 — Medium: limits can be exhausted and some state has no lifetime

The HTTP and HTTPS listeners each cap connections at 32 and set request/header timeouts, which is useful, but a public gateway is needed for wider connection and TLS-handshake abuse. Failed ordinary-key attempts use a map capped at 1,024 source identities; once filled, new identities are denied. Approved-client attempts use a map keyed by client ID and source and have the same cap. An attacker able to vary apparent source addresses can deny later legitimate sign-ins. Pending registration records have no sweep/expiry after the setup key has been consumed; approved/rejected claim records also remain until process exit. [Limits](../../apps/server/src/server-limits.mjs#L4), [ordinary attempts](../../apps/server/src/session-store.mjs#L65), [approved attempts](../../apps/server/src/approved-clients.mjs#L200), [pending records](../../apps/server/src/approved-clients.mjs#L114).

The 1,024-entry behavior is not the root cause of F1: the HTTP ordinary-key route currently avoids that limiter entirely. Fix both issues independently. A remote gateway should enforce request rates and connection budgets, and the application should age out per-source attempt and registration state.

## Controls that already work in the inspected paths

- The HTTP router serves an exact static file list, not a filesystem directory; it applies a restrictive CSP, `nosniff`, no-referrer, and `no-store` to API responses. [Router and headers](../../apps/server/src/http-app.mjs#L205).
- Diagnostics reject direct nonloopback requests. The reverse-proxy caveat is F4. [Guard](../../apps/server/src/http-app.mjs#L246).
- The approved-client password uses `scrypt`; the stored record has a verifier and hashed client secret, not plaintext password/secret. Registration and claim tokens use cryptographic randomness. [Store](../../apps/server/src/approved-clients.mjs#L37).
- Host control commands are local process messages. A client cannot invoke the manual grant through HTTP; the native input channel limits message size and pending count, and the host lease expires unless renewed. [Owner commands](../../apps/server/src/main.mjs#L421), [native input limits](../../native/media-worker/src/media-worker.cpp#L523), [lease](../../native/media-worker/src/media-worker.cpp#L371).
- The client takes connection keys from a URL fragment and removes the fragment from browser history after reading it, avoiding ordinary HTTP request/referrer leakage of that key. [Fragment handling](../../apps/web-client/src/connection-link.js#L5).

## Release gates for a remote-access mode

1. Close F1 and F2 with HTTP and runtime integration tests. Treat connection and control authorization as server-side state that is rechecked on every transition and revoked on permission change.
2. Define remote enrollment and authentication: high-entropy invitation, host approval, device-held credential/passkey, global and per-account attempt budgets, explicit live-session revocation, and clear semantics for an `approved-only` lockdown.
3. Require TLS and a public trusted certificate for remote admission; keep the HTTP listener and trust-anchor page outside public exposure. Add an explicit public hostname/origin policy and a safe proxy contract if proxies are supported.
4. Design media connectivity and firewall policy around TURN. Test candidate-directed egress and unauthenticated packets against the native ICE socket on real hardware/network paths.
5. Move or authenticate diagnostics, add public-edge connection/rate limits and monitoring, and test TLS failure behavior and certificate rotation.
6. Review pinned native GStreamer/libnice/DTLS/SRTP versions and exercise malformed SDP/ICE and data-channel input. `npm audit` does not cover those binaries.

## Verification performed

- Read the current HTTP router, authentication/session stores, access settings, runtime/control lease, TLS listener/strategies, browser client, Windows host commands, and native WebRTC/input handlers.
- Ran the local HTTP reproduction for F1 and the runtime reproduction for F2. Both produced the outcomes stated above. Ran a separate store-only removal/authentication race probe and traced the HTTP rollback and owner removal paths before classifying it.
- Ran an HTTP request-target reproduction for F3: origin-form `POST` was redirected, absolute-form `POST` was admitted over HTTP.
- `npm test`: 706 passed, 0 failed. These tests establish existing behavior; they do not establish Internet readiness.
- `npm audit --omit=dev --json`: 0 reported Node production-dependency advisories. Native components are outside this result.
- No Internet listener was started for this review.
