# Selected Internet-exposure hardening: implementation status

Updated 2026-09-24. This maps the implemented F1/F2/F3/F4/F5/F7 work to the [baseline security review](internet-exposure-review-2026-09-23.md), [current-code review](internet-exposure-review-2026-09-24.md), [remediation proposals](internet-exposure-remediation-proposals-2026-09-23.md), [selected F1/F2/F4/F5/F7 design](../superpowers/specs/2026-09-23-selected-internet-exposure-hardening-design.md), [F2/F4/F5 follow-up](../superpowers/specs/2026-09-24-revocation-and-diagnostics-isolation-design.md), and [F1/F3 LAN HTTP design](../superpowers/specs/2026-09-24-lan-http-and-fail-closed-tls-design.md). This is **not an Internet-release approval**. F6 WebRTC policy, remote enrollment, proxy/source assurance, and deployment testing remain unresolved.

| Finding                                  | Program-enforced change                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | What remains                                                                                                                                                                                                                                                                                                                                                                         |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| F1: key oracle and short-code guessing   | Removed anonymous key inspection/legacy connect routes. The metered `/api/key-start` checks budgets before lookup; eight-character purpose-neutral codes exclude `0`, `1`, `I`, `L`, and `O`. One-time/registration codes are host-issued, short-lived, single-use, and globally/per-source capped. Production injects the refreshed local scope into the HTTP router: detected eligible physical Private LANs and validated CIDR overrides govern standing-password use. Public-scoped peers cannot use it. The native dialog chooses letters-and-digits or letters-only.                              | Eight symbols remain short; bounded guessing, theft before expiry, and budget-exhaustion DoS remain. A same-host proxy/NAT can make a remote client appear local to the standing-password check.                                                                                                                                                                                     |
| F3: HTTPS downgrade and trust bootstrap  | Local HTTP binds only loopback and eligible Private-LAN addresses, never wildcard/public addresses. A live peer check and request-level scope guard reject off-link traffic. In auto/provided or invalid TLS settings, viewer/auth/session/signaling over HTTP redirect only while HTTPS is active and otherwise return no-store `503`; only valid explicit `off` serves a LAN HTTP viewer. Absolute-form targets are authority-validated; trust page/assets/status/anchor are local-peer-only on both schemes. CLI/host withhold viewer URLs and disable connect/preview when HTTPS is pending/failed. | Deliberate LAN HTTP is unencrypted. Local trust delivery remains vulnerable to an on-path LAN attacker without out-of-band fingerprint verification. Same-host proxy/NAT can launder remote sources; no remote-mode, host firewall, public-origin, or remote enrollment policy is implemented.                                                                                       |
| F2: stale or captured control permission | Current approved-client permission and generation are checked at selection, grant, native acknowledgment, and lease renewal. Any owner permission edit or removal synchronously invalidates and disconnects every affected server session before awaiting native control denial, stream/peer teardown, and persistence. Old bearers cannot start requests; protected async responses recheck session liveness. Failure shuts down sharing and invalidates remaining sessions. A separate owner action disconnects existing ordinary sessions.                                                           | Input already processed before the edit cannot be undone. Native IPC denial/peer closure is asynchronous: an in-flight input message may still arrive until denial is acknowledged or the peer is terminated. The host does not report success before teardown/persistence, and the actual worker's revoke-timeout path still needs a supported-host exercise before remote release. |
| F4: loopback-proxied diagnostics         | The public-capable HTTP and HTTPS handler returns `404` for the diagnostics page, API, and diagnostics-only assets—even for a loopback caller with a valid bearer, and before redirect. A separate `127.0.0.1`-bound listener serves diagnostics with defensive local Host/socket checks and a 256-bit, 15-minute owner-issued API bearer (at most four live). CLI and Windows host obtain its URL only on explicit action. The browser removes the URL fragment and sends the token only as an Authorization header. Ready/status/address output has no diagnostics URL or bearer.                     | A same-host proxy deliberately forwarding the private port, or theft of an unexpired bearer, remains a risk. Physical Windows-host button click, time-based expiry, and browser network-header capture remain unexercised.                                                                                                                                                           |
| F5: approved-client copy and revocation  | One approved browser/client credential may have only one live session; a second sign-in is refused without takeover. Generation is rechecked after password derivation. Permission edits/removal disconnect matching sessions immediately. UI now explains that the browser/client secret is an additional copyable credential alongside username and password, **not** a device secret or physical-device proof.                                                                                                                                                                                       | The IndexedDB secret and password can still be copied and used when no session is active. This is the intentionally chosen client-secret model for now; a future remote deployment must explicitly accept it or select a different identity model, not assume device binding.                                                                                                        |
| F7: unbounded admission work/state       | Admission uses rolling server-wide/per-source/per-identity limits, a four-job `scrypt` ceiling, finite maps, and short registration/claim/pending lifetimes. The 64-pending cap, malformed-body charging, and bounded `429`/`503` behavior are tested. TTL, attempt caps, alphabet, and eligible local networks are validated in CLI/config, not exposed as native-host controls.                                                                                                                                                                                                                       | In-process caps do not absorb volumetric TCP/TLS/WebRTC floods. A future public deployment needs an upstream edge and real-network load validation.                                                                                                                                                                                                                                  |

**Still open:** F6 has no selected remote ICE/TURN/direct-network policy. F3's code-level HTTP downgrade and trust-route exposure paths are fixed, but local HTTP trust delivery still requires an out-of-band certificate fingerprint check and cannot safely bootstrap remote clients through a source-laundering proxy. No opt-in remote mode, supported proxy policy, or remote-deployment validation exists. The [current-code review](internet-exposure-review-2026-09-24.md) covers the remaining blockers and user-management bypass audit.

Follow-up verification on this checkout: `npm test` passed 802/802, `npm run format:check`, `npm run test:host`, `dotnet build apps/windows-host/VidVnc.Host.csproj --no-restore`, the Windows navigation exercise, and `node apps/server/tests/runtime-start-check.mjs` passed. The added F1/F3 regressions cover production local-scope injection, narrow and refreshed HTTP binds, off-link request denial on keep-alive, absolute-form target validation, fail-closed HTTP admission on invalid/failed TLS, local-only trust routes on both schemes, and truthful owner viewer/trust address separation. Earlier F2/F4/F5 regressions cover synchronous affected-bearer invalidation, in-flight response denial, public-handler diagnostics `404`, and the separate local diagnostics listener. No physical host-button or hardware-media test was performed.

Earlier manual browser exercise on an isolated local server: a fresh owner-pipe capability opened the diagnostics page; its visible URL and `location.hash` were immediately free of the fragment, and the page displayed diagnostic state rather than an authorization error. Issuing four newer capabilities evicted the open page's bearer; on its next refresh the page showed “Reopen Diagnostics from the host.” This exercise preceded listener separation and demonstrates fragment handling and eviction, not the new listener's end-to-end browser flow or clock-driven expiry. The temporary server, browser tab, and test data were removed afterward.

These changes address the selected F1/F2/F3/F4/F5 concerns in the review and proposals within the stated client-secret and deliberate LAN-HTTP models. Remote access remains **not ready** until F6 and the remote-origin/proxy/trust/deployment policy are designed and verified, F5's transferable credential is explicitly accepted or replaced for that topology, and native/hardware, browser, TLS, and real-network tests are completed. Do not forward either listener to the Internet merely because the application now narrows HTTP and fails closed on unexpected TLS loss.
