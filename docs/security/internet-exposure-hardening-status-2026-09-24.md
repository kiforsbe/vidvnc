# Selected Internet-exposure hardening: implementation status

Updated 2026-09-24. This maps the implemented F1, F2, F4, F5, and F7 work to the [baseline security review](internet-exposure-review-2026-09-23.md), [remediation proposals](internet-exposure-remediation-proposals-2026-09-23.md), [selected design](../superpowers/specs/2026-09-23-selected-internet-exposure-hardening-design.md), and [F2/F4/F5 follow-up design](../superpowers/specs/2026-09-24-revocation-and-diagnostics-isolation-design.md). It is **not an Internet-release approval**. F3 HTTPS/trust-anchor and F6 WebRTC transport remain unresolved; no remote deployment profile was selected.

| Finding | Program-enforced change | What remains |
| --- | --- | --- |
| F1: key oracle and short-code guessing | Removed anonymous key inspection/legacy connect routes. A single metered `/api/key-start` checks budgets before lookup; eight-character purpose-neutral codes exclude `0`, `1`, `I`, `L`, and `O`. One-time and registration codes are explicitly host-issued, short-lived, single-use, and globally/per-source attempt-capped. The standing password is restricted to loopback or detected eligible physical Private LAN subnets, with a validated CLI/config override; a handler configured with public scope rejects it. The native Connect device dialog chooses letters-and-digits or letters-only. | Eight symbols are not high-entropy long-term credentials. A short code can be guessed within its bounded budget, stolen, or used before expiry. A same-host proxy into the **local** listener can launder its socket address; remote-mode listener/proxy separation and deployment checks are still needed. Budget exhaustion can deny legitimate attempts. |
| F2: stale or captured control permission | Current approved-client permission and generation are checked at selection, grant, native acknowledgment, and lease renewal. Any owner permission edit or removal synchronously invalidates and disconnects every affected server session before awaiting native control denial, stream/peer teardown, and persistence. Old bearers cannot start requests; protected async responses recheck session liveness. Failure shuts down sharing and invalidates remaining sessions. A separate owner action disconnects existing ordinary sessions. | Input already processed before the edit cannot be undone. Native IPC denial/peer closure is asynchronous, so the host does not report success until acknowledged; the actual worker's revoke-timeout path still needs a supported-host exercise before remote release. |
| F4: loopback-proxied diagnostics | The public-capable HTTP and HTTPS handler returns `404` for the diagnostics page, API, and diagnostics-only assets—even for a loopback caller with a valid bearer, and before redirect. A separate `127.0.0.1`-bound listener serves diagnostics with defensive local Host/socket checks and a 256-bit, 15-minute owner-issued API bearer (at most four live). CLI and Windows host obtain its URL only on explicit action. The browser removes the URL fragment and sends the token only as an Authorization header. Ready/status/address output has no diagnostics URL or bearer. | A same-host proxy deliberately forwarding the private port, or theft of an unexpired bearer, remains a risk. Physical Windows-host button click, time-based expiry, and browser network-header capture remain unexercised. |
| F5: approved-client copy and revocation | One approved browser/client credential may have only one live session; a second sign-in is refused without takeover. Generation is rechecked after password derivation. Permission edits/removal disconnect matching sessions immediately. UI now explains that the browser/client secret is an additional copyable credential alongside username and password, **not** a device secret or physical-device proof. | The IndexedDB secret and password can still be copied and used when no session is active. This is the intentionally chosen client-secret model for now; a future remote deployment must explicitly accept it or select a different identity model, not assume device binding. |
| F7: unbounded admission work/state | Admission uses rolling server-wide/per-source/per-identity limits, a four-job `scrypt` ceiling, finite maps, and short registration/claim/pending lifetimes. The 64-pending cap, malformed-body charging, and bounded `429`/`503` behavior are tested. TTL, attempt caps, alphabet, and eligible local networks are validated in CLI/config, not exposed as native-host controls. | In-process caps do not absorb volumetric TCP/TLS/WebRTC floods. A future public deployment needs an upstream edge and real-network load validation. |

Follow-up verification on this checkout: `npm test` passed 776/776, `npm run format:check` passed, `npm run test:host` passed, `dotnet build apps/windows-host/VidVnc.Host.csproj --no-restore` passed, the Windows navigation exercise passed, and `node apps/server/tests/runtime-start-check.mjs` passed. The regressions cover synchronous affected-bearer invalidation, in-flight response denial, public-handler `404` with TLS redirect enabled, and the separate local diagnostics listener. Startup verifies distinct public/private ports, token-free ready/status output, explicit owner issuance, and private API authorization. The Windows exercise verifies owner-pipe correlation and fragment URL construction but is not a physical button click or hardware-media test.

Earlier manual browser exercise on an isolated local server: a fresh owner-pipe capability opened the diagnostics page; its visible URL and `location.hash` were immediately free of the fragment, and the page displayed diagnostic state rather than an authorization error. Issuing four newer capabilities evicted the open page's bearer; on its next refresh the page showed “Reopen Diagnostics from the host.” This exercise preceded listener separation and demonstrates fragment handling and eviction, not the new listener's end-to-end browser flow or clock-driven expiry. The temporary server, browser tab, and test data were removed afterward.

These changes address the selected F2/F4/F5 concerns in the review and proposals within the stated client-secret model. Remote access remains **not ready** until F3/F6 are designed and verified against the selected network topology, F5's deliberately transferable credential is accepted or replaced for that topology, and the remaining native/hardware, browser, TLS, and deployment checks are completed. Do not forward the current listeners to the Internet merely because these five findings were narrowed or addressed.
