# POC-01 One-screen Local WebRTC Slice Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the bootstrap slice of POC-01: one dependency-free server process that displays a generated LAN password, serves its own browser client, and manages authenticated control state for one primary display.

**Architecture:** Use a small Node.js server with built-in `http` and ES modules for the first testable increment. Keep session/authentication and HTTP routing independent from the future native media boundaries; report media as unavailable until the DXGI → NVENC → WebRTC adapter is implemented on Windows/NVIDIA hardware.

**Tech Stack:** Node.js 20+ built-ins (`node:http`, `node:crypto`, `node:test`), vanilla browser JavaScript, embedded/static HTML and CSS, no third-party runtime dependencies.

**Spec:** `docs/superpowers/specs/2026-09-09-poc-01-design.md`

## Global Constraints

- Windows 11 25H2 or newer is the target server platform.
- The POC is trusted-LAN only and must not claim Internet-safe deployment.
- The POC exposes one primary display only.
- Password format is four uppercase characters, a hyphen, then four uppercase characters, for example `ABCD-EFGH`.
- Control defaults to disabled and requires an explicit browser action.
- The server process serves the browser client itself; no separate web server is required.
- Do not implement multi-monitor support, native client applications, macOS, passkeys, hub/tunnelling, production TLS, or production packaging in this plan.

### Task 2: Implement password generation and session lifecycle

**Files:**
- Modify: `poc-01/server/session-store.mjs`
- Test: `poc-01/tests/session-store.test.mjs`

**Interfaces:**
- `new SessionStore({ clock, sessionTtlMs, maxAttempts, windowMs })` creates a store.
- `store.password` returns the current formatted password.
- `store.connect(password, clientKey)` returns `{ ok: true, sessionId, controlEnabled, media }` or `{ ok: false, reason }`.
- `store.setControl(sessionId, enabled)` returns `{ ok: true, controlEnabled }` or `{ ok: false, reason }`.

- [ ] **Step 1: Implement the smallest password formatter and generator**

Use `node:crypto` random bytes and the unambiguous uppercase alphabet `ABCDEFGHJKLMNPQRSTUVWXYZ`. Format eight generated characters as `XXXX-XXXX`. Keep the generator private except for an exported `isValidPasswordFormat(value)` used by tests.

- [ ] **Step 2: Run the session tests and verify they pass**

Run:

```text
npm test -- tests/session-store.test.mjs
```

Expected: PASS for password format, authentication, disabled-by-default control, explicit enable/disable, and stop invalidation.

- [ ] **Step 3: Add expiry and failed-attempt rate-limit tests**

Use an injected clock to prove an idle session expires after `sessionTtlMs`. Use a client key to prove repeated failed passwords return `reason === "rate-limited"` after the configured threshold and that a successful connection does not reveal whether a previous attempt was close to correct.

- [ ] **Step 4: Implement expiry, rotation, and rate limiting**

Store only opaque random session IDs, expire sessions on lookup, track failed attempts per client key in a bounded time window, and have `rotatePassword()` invalidate all sessions before generating a new password. `stop()` must invalidate sessions and rotate the password.

- [ ] **Step 5: Run the complete session test file**

Run:

```text
npm test -- tests/session-store.test.mjs
```

Expected: PASS with no warnings.

### Task 3: Implement the self-served HTTP API

**Files:**
- Modify: `poc-01/server/http-app.mjs`
- Modify: `poc-01/server/session-store.mjs`
- Test: `poc-01/tests/http-app.test.mjs`

**Interfaces:**
- `createHttpApp({ serverName, display, sessionStore, webRoot })` returns an `http.Server`.
- `GET /api/info` returns the server name, one primary display, `{ state: "unavailable", codec: "H.264", transport: "WebRTC" }`, and control availability without the password.
- `POST /api/connect` accepts `{ password }` and returns `201` with a session on success, `401` for invalid credentials, and `429` for rate limiting.
- `POST /api/control` accepts `{ sessionId, enabled }` and returns `200` only for an active session.
- `POST /api/stop` rotates the password and invalidates sessions, returning `204`.

- [ ] **Step 1: Implement JSON response and request-body helpers**

Keep request bodies bounded at 16 KiB, return `400` for malformed JSON or missing fields, set `Content-Type: application/json` for JSON responses, and set `Cache-Control: no-store` for API responses.

- [ ] **Step 2: Implement the API routes**

Use the connecting request’s remote address as the initial `clientKey`. Do not put the password in `/api/info` or any response other than the server’s startup output. Do not accept control changes without a valid session ID.

- [ ] **Step 3: Run the HTTP tests and verify they pass**

Run:

```text
npm test -- tests/http-app.test.mjs
```

Expected: PASS for routing, authentication status codes, control default, stop invalidation, malformed input, and secret non-disclosure.

- [ ] **Step 4: Add the startup entry point**

Implement `server/main.mjs` to read `VIDVNC_HOST`, `VIDVNC_PORT`, and `VIDVNC_SERVER_NAME` with defaults `0.0.0.0`, `4382`, and `Studio PC`. On listen, print the selected URL, generated password, primary display profile, and a trusted-LAN warning. Keep startup output human-readable and avoid logging session secrets after the initial display.
