# HTTPS and certificate trust implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps
> use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Serve VidVNC over HTTPS with certificates provisioned automatically on first
run, an enrolment flow that gets the trust anchor onto client devices, and an explicit
path for certificates from a real CA.

**Architecture:** TLS terminates in the Node server and nowhere else. A second listener
on its own port serves TLS while the existing port stays plaintext, redirecting everything
except the enrolment endpoints. Certificate provisioning resolves through ordered
strategies — operator-provided, mkcert, Windows self-signed — and reissues whenever the
certificate is absent, expiring, or no longer covers the machine's current addresses. The
worker, GStreamer and the WebRTC peers are untouched.

**Tech Stack:** Node built-ins only (`node:https`, `node:tls`, `node:crypto`'s
`X509Certificate`), Windows certificate tooling via PowerShell, optional mkcert binary,
`node --test`, WinUI 3/.NET for the host surface.

**Spec:** `docs/superpowers/specs/2026-09-21-https-tls-design.md`

## Global Constraints

Every task's requirements implicitly include these.

- **Zero new runtime npm dependencies.** The root package declares `dependencies: {}` and
  that must remain true. Certificate issuance shells out; certificate inspection uses
  `node:crypto`'s `X509Certificate`, which exposes `subjectAltName`, `validTo`,
  `validToDate`, `fingerprint256`, `checkHost` and `checkIP`. Use `checkHost` and
  `checkIP` rather than parsing SAN text.
- **Plaintext behaviour stays intact after every single task.** At no point may a task
  leave the product unable to serve as it does today. This is what makes the work
  shippable in pieces.
- **TLS is an improvement, not a precondition.** No provisioning failure, missing tool or
  port conflict may prevent the server from starting.
- **A failure that leaves the product plaintext must be visible**, in the log and in the
  host UI. Silent degradation is the one outcome this design refuses.
- **The portable suite must keep running on Windows, macOS and Linux.** Anything requiring
  Windows tooling, mkcert, or a real handshake against issued credentials belongs in the
  opt-in hardware path, never in `npm test`.
- **No implementation code in this plan**, by author preference. Tasks describe intent,
  interfaces, and the tests that must exist; the implementer writes the code.
- Run `npm run format` then `npm run format:check` before each commit. Run only the test
  files covering what the task touched, not the whole suite, except where a task says
  otherwise.
- Commit after each task whose tests pass. Do not push unless asked.

## File Structure

New, under `apps/server/src/tls/`. The directory boundary matters: everything in it is
about obtaining and describing a credential, and nothing in it knows about HTTP routes.

| File | Responsibility |
| --- | --- |
| `local-addresses.mjs` | The machine's hostnames and current LAN addresses. Pure, injectable, portable. |
| `certificate-facts.mjs` | Reads a credential and answers: expiry, fingerprint, and whether it covers a given set of addresses. |
| `tls-settings.mjs` | Schema, defaults and validation for the TLS settings file. |
| `strategies/provided.mjs` | Loads an operator's certificate and key, or PFX. |
| `strategies/mkcert.mjs` | Detects mkcert, issues a leaf from its local CA, locates the root to serve as anchor. |
| `strategies/windows-self-signed.mjs` | Issues and exports a self-signed credential through Windows certificate tooling. |
| `ensure-certificate.mjs` | Orchestration: decide whether the existing credential still serves, pick a strategy, reissue, report which one won and why. |
| `anchor.mjs` | Which public certificate a device must trust, and its fingerprint. |

Modified: `http-app.mjs` (origin guard, plaintext allow-list, redirects), `main.mjs`
(second listener, address construction, periodic re-check), `paths.mjs` (settings file
entry), `cli/console.mjs` and the CLI configuration commands, the web client's asset list
plus a new enrolment page, and the WinUI host.

Test fixtures: a committed certificate and key pair used only by listener tests, clearly
marked as test-only.

## Task 6: Windows self-signed strategy

**Files:**
- Create: `apps/server/src/tls/strategies/windows-self-signed.mjs`
- Test: `apps/server/tests/tls/strategies/windows-self-signed.test.mjs`

**Interfaces:**
- Consumes: the strategy shape from Task 4, addresses from Task 1.
- Produces: a strategy issuing a self-signed credential through Windows certificate
  tooling, whose anchor is the leaf itself.

Three facts were verified against the real tooling during design and the implementation
depends on all three: a certificate can be issued carrying IP address entries in its
subject alternative name as well as DNS names; it exports to PFX; and `node:tls` consumes
that PFX directly with no conversion to PEM. Do not add a PEM conversion step.

The issued certificate must not be left behind in the user's certificate store. Whatever
is created there during issuance is removed once exported, so repeated startups do not
accumulate certificates.

- [ ] **Step 1: Write the failing tests** against a fake runner. Cover: the SAN request
      includes every discovered hostname and IP, with IPs expressed as IP entries and not
      as DNS names; the export produces a credential the loader accepts; a tooling failure
      is reported as a reason with the tool's message; the temporary store entry is
      cleaned up on success and also on failure; the strategy reports unavailable on
      non-Windows platforms rather than throwing.
- [ ] **Step 2: Run them and confirm they fail.**
- [ ] **Step 3: Implement.**
- [ ] **Step 4: Run the tests and confirm they pass.**

## Task 8: The origin guard

**Files:**
- Modify: `apps/server/src/http-app.mjs` — the origin comparison
- Test: `apps/server/tests/tls/origin.test.mjs`

**Interfaces:**
- Produces: a pure decision — given the scheme a request arrived on, the host header and
  the `Origin` header, is this request acceptable?

This is the highest-risk change in the work. Too strict breaks every request loudly, which
is survivable. Too loose removes the protection with no symptom, which is not. Extract the
decision into a pure function specifically so it can be tested exhaustively, then have the
request path call it.

The defect to defend against is documented in the spec: browsers omit the port from
`Origin` when it is the scheme's default, so an expected origin that always appends a port
never matches on 443, and every request fails with no obvious cause.

- [ ] **Step 1: Write the failing tests as an exhaustive table.** Cover the cross product
      of: scheme `http` and `https`; default port for the scheme, non-default port, and no
      port in the host header; `Origin` present and matching, present and differing only
      by scheme, present and differing only by port, present and pointing at another host,
      and absent entirely. Include explicitly: an HTTPS request on 443 whose `Origin`
      carries no port is accepted; the same request whose expected origin was built with
      `:443` appended would have been rejected, so the test would catch a regression to
      the naive form; an HTTP request whose `Origin` claims `https` on the same host is
      rejected; a request with no `Origin` follows whatever the current behaviour is, and
      that behaviour is asserted rather than assumed.
- [ ] **Step 2: Run them and confirm they fail.**
- [ ] **Step 3: Implement**, changing only the comparison and leaving the surrounding
      request handling alone.
- [ ] **Step 4: Run the tests and confirm they pass.**
- [ ] **Step 5: Run the whole server test suite**, not just this file. This function sits
      in the path of every request, so the blast radius of a mistake is the entire API.
- [ ] **Step 6: Format, then commit.**

## Notes for the implementer

- Tasks 1 through 3 are pure and independent; they can be done in any order or in
  parallel. Everything from Task 4 onward depends on them.
- Tasks 8 through 10 change existing behaviour rather than adding to it, and are the ones
  most likely to break something that works today. Run the full server suite after each.
- Task 8 deserves more care than its size suggests. It is a small change in the path of
  every request, and its failure mode is silent.
