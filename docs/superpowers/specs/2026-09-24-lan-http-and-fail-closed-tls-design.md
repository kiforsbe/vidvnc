# LAN-only HTTP and fail-closed TLS (F1/F3) — design

Date: 2026-09-24. Status: proposed for written-spec review. This design implements the owner's choices after the [current security review](../../security/internet-exposure.md): fix F1's production LAN-scope wiring; make HTTP accessible only through loopback or eligible physical Private-LAN interfaces, with both narrow binds and peer checks; retain full LAN HTTP **only** when TLS was deliberately configured `off`; and close the remaining F3 plaintext fallback, request-target, and remote trust-enrollment paths. It does not claim the application is ready for Internet exposure or solve F6 WebRTC routing.

## Existing behavior and root causes

`main.mjs` creates and refreshes a local-session scope, but hands it to `StreamRuntime`, which does not use it. `createHttpApp` instead constructs its empty-adapter default, allowing the standing password only from loopback. The same main process binds one plaintext server to `VIDVNC_HOST || '0.0.0.0'` before attempting TLS. The TLS listener deliberately treats provisioning/bind failure as a nonfatal plaintext fallback. Invalid TLS settings also become an `off`-shaped state with an `invalid` marker. The HTTP router redirects only request targets beginning with `/`; a valid absolute-form target reaches the normal route. Trust pages/assets and the public certificate anchor remain unredirected on HTTP and are also reachable on HTTPS without a local-peer condition. Existing tests assert parts of this legacy behavior and must be changed, not merely supplemented.

## Security contract

1. No application plaintext response is available to a nonlocal peer. HTTP sockets bind only to `127.0.0.1`, `::1` when supported, and the host IPs of eligible, up, physical Ethernet/Wi-Fi adapters with a Windows Private profile and private IPv4/ULA network. No HTTP listener binds `0.0.0.0`, `::`, a public address, a virtual/VPN adapter, or a link-local address. A peer-address check independently rejects out-of-scope connections and requests, including on sockets opened before a LAN profile changes. The local network detector's failure state means loopback-only.
2. The existing `localSessionNetworks` CLI/config override continues to narrow **peer** eligibility to detected on-link private networks; it does not remove an otherwise eligible host interface address from the bind list. Loopback remains eligible. The detected scope is the one actually passed to `createHttpApp`, fixing F1; its refresh is shared by standing-password admission, HTTP peer checks, and trust-route locality.
3. `VIDVNC_HOST` remains the HTTPS bind preference and may only narrow HTTP's nonloopback eligible bind set: its default/wildcard value permits all eligible LAN addresses; an explicit eligible IP permits only that LAN IP; a loopback value permits no LAN IP. Other explicit values leave HTTP loopback-only and produce an operator warning. It never makes HTTP bind a public address. Loopback HTTP remains available for local host management/enrollment regardless of that setting.
4. Unless TLS is **validly and deliberately** configured `off`, no viewer page, ordinary/approved admission, bearer API, or media signaling is processed over HTTP while TLS is inactive. Those requests return a generic, no-store `503` until HTTPS is actually listening. A configured `mode: off` with no `invalid` marker is the sole exception: it deliberately serves the full application over **LAN-only** HTTP, preserving that selected function. A failed first TLS attempt, certificate mismatch, TLS port conflict, later HTTPS listener loss, and invalid settings all obey the same fail-closed rule. A failed certificate re-check that leaves the previous HTTPS listener serving does not disable the still-working HTTPS service.
5. When TLS is active, local HTTP serves only the fixed trust-enrollment page/assets and trust status/anchor; other origin-form paths receive an uncached 307 to the live HTTPS port. Every absolute-form target is parsed and its scheme/authority checked against the actual socket and accepted `Host` before routing or redirecting. A matching plaintext absolute-form target for a non-trust path redirects to the corresponding HTTPS path/query; a mismatch or malformed/non-applicable target is rejected, never dispatched to an API. No request-target form can execute a sensitive route on HTTP in auto/provided mode.
6. The fixed trust-enrollment routes (including static assets, status, and anchor download) require a local-scope peer on **both** HTTP and HTTPS. Remote HTTPS clients receive no trust page or anchor from the application. The anchor remains public certificate bytes, not a private key. A user who needs to trust a self-signed remote endpoint must obtain and verify the certificate/fingerprint through an independent trusted local or out-of-band channel; this design does not invent a remote bootstrap.
7. The diagnostics API remains on its separate loopback-only port and absent from every main HTTP/HTTPS listener. No new public management route, forwarding-header trust, remote mode, TURN service, or device credential is introduced.

## Components and lifecycle

### Local-scope controller

Extend `local-session-scope.mjs` to expose a read-only list of eligible **host bind addresses** from the same Windows-adapter snapshot it uses for peer CIDRs. Keep these concepts separate: a narrow peer override may exclude the host's own IP but clients in that CIDR still reach the host via its eligible interface address. `update()` replaces both views atomically. A failed or off-link detection/override never expands peer access. The peer check remains based on the socket address, not `Forwarded`/`X-Forwarded-For`.

### LAN HTTP listener manager

Use one shared HTTP request handler and session/admission state, with one bounded `http.Server` per eligible bind address. The manager initially binds loopback, then eligible LAN IPs, and reconciles against each refresh. Scope becomes restrictive **before** removing bindings, so requests on stale keep-alive sockets fail even during a reconcile. Removed listeners stop accepting and close their existing connections; newly eligible addresses are attempted individually. A bind error for one LAN address is logged and never causes a wildcard fallback. Failure to bind required `127.0.0.1` is a startup error, matching the current plaintext-port conflict behavior. Stop/shutdown closes every HTTP listener and the separate diagnostics/TLS listeners. The manager reports the actually bound addresses for CLI/host presentation, not merely every address returned by `networkInterfaces()`.

### Router and TLS state

`createHttpApp` receives the refreshed local scope and an explicit plaintext policy derived from validated TLS settings (`off` only when deliberate, not `invalid`). It checks the actual socket's encryption state and peer address before path dispatch. Connection-level rejection on each HTTP listener reduces exposure; request-level checks are still required for keep-alive sockets and tests that call the shared handler directly. Do not use client-controlled forwarding headers as evidence of encryption or locality. Route parsing validates absolute-form target authority/scheme before applying the redirect or trust allowlist. The trust locality check precedes static files and trust API responses, so no alternate method or request form bypasses it.

Keep TLS provisioning asynchronous so the owner UI is not blocked by certificate tooling, but startup and status/host UI must no longer advertise a usable **viewer** address on HTTP while auto/provided HTTPS is pending or failed. Distinguish local trust/enrollment addresses from viewer addresses, and show HTTPS as pending/unavailable with a sanitized reason. When HTTPS comes up, advertise the live HTTPS viewer address; if it is later lost, withdraw the viewer address rather than returning to HTTP. Deliberate TLS-off mode advertises only bound LAN HTTP viewer addresses. The Windows host's overview, preview, QR/address controls, and CLI banner must not claim that failed HTTPS implies working HTTP pairing. The private diagnostics URL/token remain separate and undisclosed in public status output.

## Tests and acceptance criteria

Write failing tests before implementation for each behavior. In particular:

- A production-startup assembly test proves the refreshed LAN scope reaches the HTTP handler; an eligible LAN peer can use the standing password, while an off-link peer and a `public`-scoped handler cannot. Do not rely only on scope-component unit tests.
- Listener-manager tests with injected adapter snapshots and ephemeral ports prove bind addresses are only loopback/eligible physical Private LAN IPs; an explicit `VIDVNC_HOST` narrows; profile change/detection failure closes obsolete listeners and denies requests on existing sockets; one LAN bind error does not fall back to wildcard; shutdown closes all.
- Raw HTTP and HTTPS tests cover normal and absolute-form request targets, matching/mismatched authority, origin-form redirects, TLS inactive/active transitions, invalid settings, and explicit `off`. An inactive auto/provided listener must never serve `/`, `/api/info`, `/api/key-start`, approved sign-in, a bearer route, or a stream offer via HTTP. A matching absolute-form POST cannot execute `/api/key-start` over HTTP.
- Trust routes/assets are reachable from eligible local peers, denied to remote peers on both schemes, and never leak a private key. Existing diagnostics `404` tests remain true on every main listener.
- Address/status and Windows-host navigation tests show truthful pending/failure/recovery and intentional-off states; no HTTPS failure is worded as full HTTP fallback. Run the full Node suite, formatting, host tests/build, runtime-start check, and focused raw-socket tests. A real Internet scan, hardware WebRTC run, physical NIC/profile transition, and native media test remain separate release validation.

Update the [current security review](../../security/internet-exposure.md), [implementation status](../../security/internet-exposure.md), README/architecture as needed, and `CHANGELOG.md` after implementation. Mark F1's wiring issue closed only after the production-assembly regression passes; mark F3's code paths closed only after the fail-closed, locality, and absolute-form tests pass. Keep F6 and remote-release approval open.

## Residual risk and non-goals

Narrow binding plus peer checks cannot identify the original remote user behind a same-host reverse proxy or a router that rewrites the source into an allowed LAN address. The application must not claim that a socket-locality test defeats such forwarding; deployment guidance must prohibit proxying the local HTTP/trust listener and require host/router firewall checks. A self-signed certificate still requires genuine out-of-band fingerprint verification. The HTTPS main listener may remain reachable according to `VIDVNC_HOST` and external firewall configuration; this change is not an opt-in Internet mode and does not resolve F6's direct WebRTC/ICE transport policy. No public hostname, public CA certificate, TURN service, passkey, or device-bound identity is required or added by this design.
