# Selected Internet-exposure hardening design

Date: 2026-09-23. Status: selected design; see the [implementation status](../../security/internet-exposure-hardening-status-2026-09-24.md) for current controls and remaining verification.

The [2026-09-24 follow-up design](2026-09-24-revocation-and-diagnostics-isolation-design.md) supersedes this document's F2/F4/F5 implementation details: permission edits now disconnect active sessions, diagnostics uses a separate loopback listener, and the retained secret is explicitly a browser/client credential additional to username and password.

This design addresses the selected concerns F1, F2, F4, F5, and F7 from the [Internet exposure review](../../security/internet-exposure-review-2026-09-23.md) and its [remediation proposals](../../security/internet-exposure-remediation-proposals-2026-09-23.md). It hardens the existing LAN-oriented service before any remote deployment profile is chosen. It does **not** authorize Internet exposure: F3 (HTTPS failure and trust enrollment) and F6 (WebRTC media/network policy) remain open, and F5 remains a transferable credential by the owner's explicit choice.

## Intent and security contract

The owner wants code-enforced defenses against online key guessing, stale control permission, loopback-proxy diagnostics exposure, approved-client revocation gaps, and unbounded admission work, while preserving the current approved-client secret and existing local-host administration. No public hostname, TURN service, passkey, VPN, or remote-mode architecture is selected by this work.

Success means:

- No separate anonymous key-validity oracle confirms whether a submitted connection key exists, and every authentication request is budgeted before key lookup or expensive password verification.
- A current `view-only` or removed-client decision prevents new native control grants, ends an existing lease, and is not reported successful to the host until the native denial or peer termination is confirmed.
- A request forwarded by a same-host proxy with a loopback socket address and `Host: localhost` cannot retrieve live diagnostics without an owner-issued capability.
- One approved credential has at most one live session; removal invalidates new admission and terminates all of its active sessions. This is session containment, **not** device binding.
- Admission counters, password-derivation concurrency, and registration claims have finite bounds and lifetimes. In-process limits protect host resources but do not replace an upstream DDoS edge.

## Scope and approach

Use focused security primitives within the current Node server, browser client, and Windows host. Avoid a wholesale remote-listener, identity, or WebRTC rewrite. Authentication limits belong in a shared request-admission component, not separate route-specific maps. The request handler must carry an explicit listener scope so a future public listener cannot accept the standing session password, even when its immediate peer is a same-host proxy. Current permission belongs in the authorization decision for every control transition, not a value captured only at connection time. Diagnostics obtains a capability from the local owner command channel; public HTTP headers and socket locality are defense in depth, not the credential.

The rejected alternatives are (1) route-by-route patches that leave alternate entry points and asynchronous races and (2) a full remote-mode/identity redesign that would implicitly decide F3/F6 and the deployment profile. Neither is needed to implement these selected safeguards. The second may be needed later for a remote release.

## F1 and F7: connection keys and bounded admission

### Key dispatch and key strength

Remove `POST /api/connection-key`. Generate exactly eight independent random symbols per code, with no purpose encoded in any symbol. The preferred **letters and numbers** alphabet has 31 uppercase symbols (`23456789ABCDEFGHJKMNPQRSTUVWXYZ`), deliberately excluding `0`, `1`, `I`, `L`, and `O`; it provides about 39.6 bits. The optional **letters only** alphabet is `ABCDEFGHJKMNPQRSTUVWXYZ` (23 symbols), also excluding `I`, `L`, and `O`; it provides about 36.2 bits rather than the present purpose-constrained ~34.7 bits. Other font-dependent lookalikes can still exist, so host/browser UI uses a clear monospaced font and copy/QR remains available. The browser accepts either as eight case-insensitive characters; it removes display grouping but does not silently translate one valid character into another. A single metered start endpoint looks up the key _after_ admission checks and dispatches internally: a local session password or one-time connection key creates one session; a client-setup key is consumed and yields a separate, high-entropy, short-lived registration ticket for completing the form. Invalid, malformed, and expired keys all receive the same generic error. There is no read-only key-inspection request.

Preserve the standing, multi-use **session password for local sessions only**, as the owner requested. “Local” means the same host or a directly connected, private Ethernet/Wi-Fi LAN subnet selected from the host's active interfaces—not every RFC 1918/private address, a VPN/virtual adapter merely labeled private, or a client-supplied forwarding header. On Windows, the default detector requires an active physical Ethernet/Wi-Fi adapter, a Private network profile, an on-link netmask/prefix, and an RFC 1918 IPv4 or unique-local IPv6 address. It excludes public, link-local, tunnel, and virtual interfaces. If classification is uncertain or no eligible interface exists, it allows loopback only and reports why. A CLI/config override may select a narrower CIDR or an eligible detected LAN subnet but may not broaden session-password access to an arbitrary public/off-link CIDR. The request handler checks the actual socket peer against that scope; a future public/remote HTTPS listener must set a separate listener scope that _always_ rejects the session password, including connections forwarded from a same-host proxy. A LAN-bound listener and a Windows Firewall rule restricted to the selected subnet provide supporting network boundaries. A same-host proxy deliberately forwarding public traffic into the **local** listener can still launder the peer address; locality cannot be proven from the socket alone. This remains an explicit deployment restriction and remote-mode preflight condition, not a claim that an IP check defeats such a proxy.

At most one **ephemeral** short code (one-time connection or client setup) is active at a time. The local host UI shows an explicit **Generate one-time code** or **Generate client-registration code** action; opening the connection dialog or merely switching its type does not mint one. The CLI requires an explicit owner command. Issuance invalidates any earlier ephemeral code. A code expires five minutes after issuance by default (subject to the bounded CLI/config setting below), is consumed once, and is never silently renewed. The host shows a countdown, clears expired code/QR/copy controls, and requires a fresh owner action to issue another. The one-time connection code creates one session. Redeeming a client-registration code while valid consumes that code and returns a separate 256-bit registration ticket with a ten-minute lifetime, so form entry and local owner approval can proceed without extending the guessable code's lifetime. Approved-client sign-in remains the intended unattended path **once remote access is separately secured**; this design does not enable a remote mode. The browser and host keep copy/QR and eight-character manual entry. Legacy letter-only codes need not remain valid across the version update because keys are process-ephemeral.

The native **Connect device** dialog offers a per-issuance **Code characters** choice: **Letters and numbers (recommended)** or **Letters only**. This applies to newly generated one-time and registration codes. For the standing local session password, selecting a different alphabet requires an explicit **Regenerate session password** action; it invalidates the old password for new connections but does not disconnect existing sessions. The dialog shows the resulting code and its security/expiry status, not controls for the expiry, attempt limits, or LAN CIDRs. The CLI/config default alphabet is letters and numbers; the host's selection overrides it only for that issuance.

### Admission boundary

Add one bounded admission controller in front of JSON body parsing for the new `/api/key-start`, `/api/approved-clients/register`, and `/api/approved-clients/sign-in`. It charges every request, including malformed bodies, before any key lookup or `scrypt` work. Use the actual socket peer as the source unless a separately designed trusted-proxy configuration is added; do not accept `X-Forwarded-For` as identity. After parsing, apply an additional per-approved-client-ID budget to sign-in, including unknown IDs. A separate, higher polling budget covers `/api/approved-clients/status`, which uses a 256-bit claim token and legitimately polls during approval. Responses are generic `429` with `Retry-After`; an unauthenticated caller cannot infer whether a key or client exists from a limit response.

Each newly issued ephemeral code starts a server-wide budget of 20 failed short-code submissions across all sources by default, with at most five from one socket source. Once the global budget is spent, ephemeral-code admission is disabled until the owner explicitly issues a new code; expiry does not automatically reset it into another active code. With one active code and no leakage or bypass, 20 independent guesses succeed with probability approximately `20 / 31^8` (2.3 × 10⁻¹¹) for letters and numbers, or `20 / 23^8` (2.6 × 10⁻¹⁰) for letters only. The local standing session password has a separate 20-failure global budget per password generation by default; exhaustion suspends it until the local owner rotates it. These are availability/security trade-offs: a bot that reaches the relevant listener can intentionally exhaust a budget and deny a legitimate attempt. The host must show lockout and offer owner-controlled regeneration; it must never fail open. Independently, approved-client sign-in and registration-ticket submission have 10 requests per source and 120 total per server per rolling minute; sign-in also has 10 per claimed client ID per rolling minute. At most four `scrypt` jobs run concurrently. Status polling permits 60 requests per source and 600 total per minute. Saturated `scrypt` capacity returns `503` with a short retry interval rather than queueing unbounded work. Counters use monotonic time, have a fixed maximum of 1,024 source/identity entries, sweep expired entries, and evict the oldest entry when full; the global budget remains authoritative under identity rotation. Existing socket/header/body limits remain in force.

### CLI and configuration settings

Extend the existing validated `access-settings.json` schema and CLI rather than introducing editable native-host controls for these thresholds. The default and allowed values are:

| Field                           | Default          | Valid range / meaning                                                                                                                  |
| ------------------------------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `shortCodeTtlSeconds`           | `300`            | Integer `60`–`600`; applies to newly issued one-time and client-registration codes, not the local standing session password.           |
| `shortCodeMaxFailures`          | `20`             | Integer `1`–`20`; global failed-attempt cap for each ephemeral-code issuance.                                                          |
| `shortCodePerSourceMaxFailures` | `5`              | Integer `1`–`5`, never greater than `shortCodeMaxFailures`; per-socket-source cap for an issuance.                                     |
| `sessionPasswordMaxFailures`    | `20`             | Integer `1`–`20`; global failed-attempt cap until the local session password is rotated.                                               |
| `defaultCodeAlphabet`           | `letters-digits` | `letters-digits` or `letters`; used for a startup local password and CLI-issued codes unless an explicit issuance choice overrides it. |
| `localSessionNetworks`          | `auto`           | `auto` or an array of CIDRs restricted to eligible, currently detected on-link private LAN subnets. Loopback always remains allowed.   |

Add read/set CLI commands `code-ttl`, `code-attempts`, `code-source-attempts`, `session-password-attempts`, `code-alphabet`, and `local-session-networks` through the existing access-settings transaction path; each accepts no argument to show the current value or one validated argument to set it. Add explicit live-owner commands `one-time-code [letters-digits|letters]`, `registration-code [letters-digits|letters]`, and `session-password rotate [letters-digits|letters]`. The latter rotates the password for new local connections without ejecting live sessions. Direct JSON edits are validated at startup: malformed/out-of-range values prevent service startup; a syntactically valid but currently off-link `localSessionNetworks` list restricts the standing password to loopback and raises a host warning rather than reverting to automatic LAN access. A CLI change to TTL or attempt counts applies to the **next** issued code or rotated password; it cannot retroactively extend an active code's expiry or enlarge its remaining guess budget. The native host may display the effective expiry and lockout state but exposes no controls for the TTL, budgets, or CIDRs; its only new choice is the alphabet in Connect device.

Registration submission validates shape and the one-use registration ticket before consuming a `scrypt` slot. Only one successful submission consumes the ticket. `ApprovedClientStore` caps live pending requests at 64 and gives pending requests a ten-minute TTL. Rejected claim state expires after ten minutes; approved claim delivery also expires after ten minutes. If an approved credential is never claimed by expiry, remove the orphaned approved record so a stale approval cannot linger in the host list. Cleanup runs on access and a periodic sweep; persistence failure leaves an unclaimed credential unusable and surfaces a host error rather than silently extending its lifetime.

These controls bound application work. A rotating-source adversary can still exhaust a global budget and deny service, and a desktop process cannot absorb a large TLS/connection flood. The [proposal's F7 SecRAC](../../security/internet-exposure-remediation-proposals-2026-09-23.md#f7--bound-public-resource-use-and-make-admission-state-expire) for an upstream edge remains applicable to any future public deployment.

## F2: current permission and native-control revocation

Approved-client records have an in-memory authorization generation. A `view-only` change or removal invalidates the old generation synchronously when the local owner command is accepted, before queued file I/O. The runtime drops the affected sessions' automatic-control eligibility immediately. Every manual/automatic grant and lease renewal checks the current record, current generation, live session, live stream, and worker state. No grant may rely solely on the permission captured in `onConnect`. A final check after each asynchronous native grant closes the downgrade-during-grant race.

For a downgrade, serialize native lease revocation with grants and await native `setPermission(false)` acknowledgment before returning success to the Windows host. If the worker does not confirm denial within a bounded timeout, tear down the affected peer/stream and report a failed host action; do not leave a control-capable peer attached. Client removal likewise invalidates admission, disconnects all of its sessions, and awaits stream/control teardown. Persist the new permission/removal before returning host success. If the security-state write fails, keep current-process access denied, stop sharing if a safe durable state cannot be assured, and show a host error rather than rolling back into live control. The host UI must not show a completed downgrade while native control is still active.

Changing the _future sign-in mode_ to `approved-only` remains distinct from disconnecting already admitted ordinary sessions. The host UI must state that distinction. A separate explicit **disconnect existing ordinary sessions** action will revoke those sessions and their streams when the owner needs immediate lockdown; changing the mode alone will not silently become that action.

## F4: owner-capability diagnostics

`GET /diagnostics` may continue to serve a nonsensitive page shell on loopback, but `GET /api/diagnostics` requires both the existing loopback/Host guard and a 256-bit random, process-memory owner capability. The local owner channel mints a short-lived capability on demand (15 minutes, at most four outstanding). The Windows host obtains one when the owner clicks Diagnostics; the CLI offers an explicit local command rather than placing a capability in routine startup output or logs. The returned local URL places the capability only in a fragment. Browser JavaScript reads it once, removes the fragment with `history.replaceState`, holds it only in memory, and sends `Authorization: Bearer` for diagnostic refreshes. The server compares a stored hash in constant time, uses `no-store`, and never accepts a capability from a query string, cookie, `Host`, or forwarded header. Expired/missing capabilities return generic `403` without live data; the page tells the owner to reopen it from the host.

The token is a bearer credential: a person who obtains it during its lifetime could retrieve diagnostics through an exposed proxy. Short lifetime, host-only issuance, fragment delivery, no logging, and the existing local guard reduce that risk. A separate management listener or native-only diagnostics UI may be adopted in a future remote-mode design; this change removes the current _unauthenticated_ loopback-proxy bypass without claiming that a proxy can never forward an authenticated request.

## F5: approved credential and session lifecycle

Keep the current IndexedDB client secret and password verifier. Call it an **approved browser credential**, not a cryptographically bound device. `installationId` remains display metadata and is not used as an authentication proof. No passkey/WebAuthn or credential migration is introduced. The host continues to approve enrollment locally and can revoke the credential by removing its approved-client record; reenrollment is the rotation path.

`SessionStore.connectApproved` rejects a second live session with the same approved-client ID. It does not evict the existing session, because a copied credential must not be able to kick out its legitimate user. A clean disconnect permits immediate sign-in; an abrupt close may require the existing 20-second session TTL to elapse or owner-side revocation. The client presents a clear authenticated “already in use” message. The host shows the active session and offers the existing remove/disconnect action.

Authentication captures a record generation before `scrypt`, then verifies that the same approved record and generation still exist afterward. The HTTP handler revalidates immediately before session creation, with no intervening `await`. A removal intent invalidates the generation synchronously; all matching sessions are disconnected and their streams/control closed before the host sees removal success. If removal races the post-admission `markConnected` write, the new session is rolled back. Test this ordering with controlled promises, not timing guesses.

This narrows the F5 review finding but does **not** eliminate credential cloning: a copy of the IndexedDB secret plus password can still sign in when no session is active. The remote-profile proposal's device-held proof requirement is deferred by the owner's choice. It remains a release decision, not a completed control.

## Failure handling and observability

All admission failures avoid key/client existence detail. `429` and `503` include bounded retry guidance; they do not silently fall through to another route. Security counters and audit records contain route class, reason, time, and coarse source information only—never raw keys, passwords, client secrets, claim tokens, diagnostics capabilities, SDP, or session bearers. A host-visible status distinguishes a rejected request, a temporary budget exhaustion, and a permission/revocation operation that failed to persist or reach the native worker. Capability and registration sweeps are safe to run repeatedly.
