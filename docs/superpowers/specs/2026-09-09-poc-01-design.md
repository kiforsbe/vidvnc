# POC-01 design · revised 2026-09-11

## Approved target

Windows 11 25H2+ / NVIDIA server, primary desktop capture, hardware H.264 over
WebRTC to a browser served by the same server, generated readable password,
mouse and keyboard, manual same-LAN URL. No Windows GDI/MJPEG fallback.

## Implementation

Node.js owns HTTP, assets, password/session policy and one native child worker.
C++/GStreamer owns DXGI, GPU conversion, NVENC, RTP/WebRTC and Windows input.
The browser is plain HTML/CSS/JavaScript. Separate languages keep policy readable
without moving pixel data through JavaScript. One command launches both pieces;
this is not yet a single-process or packaged executable.

1. Preflight validates Windows build, GPU plugins and actual primary resolution.
2. Host prints LAN URLs and newly generated password.
3. Browser authenticates, reserving one session; input defaults off.
4. Browser offers receive-only H.264 plus ordered input data channel.
5. Authenticated HTTP starts the worker; full SDP answer includes gathered ICE.
6. GPU-captured frames flow directly through native H.264/RTP to WebRTC.
7. Browser fits the video with aspect-ratio preservation and excludes letterbox
   regions from pointer coordinate mapping.
8. Explicit control opt-in activates the native input sink. Blur, Esc, control
   disable, disconnect, data-channel loss and heartbeat expiry release held input.
9. Session revocation stops the worker; EOF from the owner also stops capture.

## Per-session stream profiles

The server accepts a requested profile at connection time and returns the
selected immutable profile. `auto` detects iPhone/iPad user agents; explicit
profiles override detection. Each native worker applies its own width, height,
frame rate, CBR bitrate, and 1,200-byte RTP MTU. Initial profiles are desktop
(2560×1440/30/6000 kbps), balanced (1920×1080/30/4000), mobile
(1280×720/15/2000), and low-bandwidth (960×540/15/1000). This per-session
boundary allows different clients to use different quality without global
reconfiguration. Adaptive mid-session switching is later work.

## HTTP contract

- `GET /`, `/app.js`, `/style.css`: self-hosted client, no third-party assets.
- `GET /api/info`: name, actual primary monitor and readiness; no credentials.
- `POST /api/connect {password}`: 201/token, 401/auth failure, 429/rate limit,
  409/already occupied. Starts view-only.
- `POST /api/offer {sdp}`: bearer-authorized, starts native negotiation.
- `POST /api/heartbeat {}`: bearer-authorized lease renewal.
- `POST /api/disconnect {}`: bearer-authorized session-only revocation.
- No unauthenticated `/api/stop`; host termination is local.

Control, key, pointer, wheel, release and ping messages use the peer data channel.
Only its authenticated worker may inject input. Enforce bounds and key allowlist
in native code, not solely in browser JavaScript.

## Security and Windows limitations

HTTP is explicitly trusted-LAN-only, not authenticated/encrypted transport.
WebRTC encryption does not repair insecure page delivery/signaling. Production
requires HTTPS/trusted pairing, stronger credentials and audit/revocation UX.
Current mitigations: same-origin/known-host validation, request size/time limits,
constant-time password check, bounded attempt history, one client and short leases.

Windows build floor 26200 enforces 25H2+. NVIDIA encoder absence fails closed;
never switch silently to a fallback. Secure desktop/UAC/higher-integrity windows
and secure attention sequences cannot be controlled with ordinary SendInput.
No Windows service mode, login-screen access or privilege elevation is included.

## Acceptance and remaining work

Native build, automated policy/native pipeline tests and visible real browser
video are required evidence, not just an HTTP success code or peer connection.
Cross-device input, keyboard layouts, network loss and performance still require
hands-on validation. Current host shell is console-only: the requested native
WinUI 3 onboarding window remains unfinished; do not describe the entire POC as
finished until that and acceptance checks are handled.

No macOS server, native clients, multiple monitors, passkeys, hub/tunneling,
production installer or adaptive bitrate in this increment. Product-level native
Windows UI must use real WinUI 3; Apple UI must use the native macOS frameworks.
